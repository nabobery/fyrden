# Limits

What a Fyrden deployment accepts and serves for git, why, and which limits an
operator can change. Engine metrics are described in [metrics.md](metrics.md).

Every number on this page is one of three kinds:

- **Platform limit:** set by Cloudflare. Linked to Cloudflare's documentation;
  it can change without a Fyrden release.
- **Measured:** observed by the Fyrden project on a real deployment, with the
  date and plan. Paid-plan measurements have not been made yet unless stated.
- **Default:** a Fyrden setting chosen as a starting point. Defaults may change
  in later releases as they are tuned under load. Those with a variable can be
  set per deployment (see [Configuration variables](#configuration-variables)).

## Push

### Request body limit

Cloudflare refuses a request whose body is larger than the zone plan allows,
before the Worker runs, with its own HTTP 413 page. Fyrden cannot change that
answer or show a better message.

| Cloudflare plan of the hostname | Request body limit |
|---|---|
| Free, Pro (and `*.workers.dev`) | 100 MB ([platform limit](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits)). **Measured** on 2026-10-10 on Workers Free, `workers.dev`: exactly 104,857,600 bytes (100 MiB) accepted, 104,857,601 refused, both with and without `Content-Length` |
| Business | 200 MB ([platform limit](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits)); not measured |
| Enterprise | Up to 5 GB, set on the zone ([platform limit](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits)); not measured |

A push is one request, so a stock `git push` whose request is larger than the
limit fails with an HTTP 413 error. No refs change and nothing is stored,
because Fyrden never saw the request.

Use `fyrden push` instead of `git push` for large pushes:

- `fyrden push <remote> <refspec...>` builds the pack git would send, checks its
  size first and, when it fits, runs `git push`. When it does not fit, it stops
  and names the limit and `fyrden push --chunked`.
- `fyrden push --chunked <remote> <refspec...>` uploads the pack in parts
  through an upload session (each part one request under the limit, retried on
  failure), then completes the session, which checks and commits it exactly as
  a push.
- Both forms talk to the remote's push URL (`remote.<name>.pushurl`, else its
  `url`), as `git push` does; a remote with several push URLs is refused, so
  name the URL instead. The token is `FYRDEN_TOKEN`, else the password in
  the push URL, else what git's credential helpers have for it. A token the
  CLI holds reaches its own `git` calls through a helper set for that one
  call, never in a URL or on the command line.
- The CLI assumes 104,857,600 bytes. On a Business or Enterprise zone, pass
  `--body-limit <bytes>` or set `FYRDEN_PUSH_BODY_LIMIT`, and raise
  `GIT_PUSH_MAX_BODY_BYTES` on the server to match.

The server's own check, `GIT_PUSH_MAX_BODY_BYTES` (default 104,857,600), refuses
a larger push with a git error message rather than a 413, for bodies the edge
let through.

How a push body is stored is the same on every plan: the Worker writes the
request body to R2 with one upload, and the repository's Durable Object reads,
checks and indexes it from there. An uncompressed body with a
`Content-Length` (what git sends behind Cloudflare's edge) is streamed to R2
as it arrives: the Worker runs no code per chunk. Two kinds of body are read
into the Worker's memory first, since their length is known only at the end:

- **Compressed bodies** (`Content-Encoding: gzip`; JGit and EGit compress
  every push, git never does). The Worker inflates the body and holds the
  inflated bytes, inside an isolate's 128 MB of memory
  ([platform limit](https://developers.cloudflare.com/workers/platform/limits/#memory)),
  so their limit is lower: `GIT_PUSH_MAX_GZIP_BODY_BYTES`, default 33,554,432
  (32 MiB) of inflated bytes, or `GIT_PUSH_MAX_BODY_BYTES` if that is smaller.
  A larger compressed push is refused with a git error message naming the
  limit. Push it uncompressed (with git) or with `fyrden push --chunked`.
- **Bodies without a `Content-Length`** (chunked transfer encoding). The edge
  supplies the length on a deployment (**measured** on 2026-10-10 on Workers
  Free), so this happens only without it, as under `wrangler dev`.

### Objects and packs

| Limit | Value | Kind |
|---|---|---|
| Largest object, delta base or delta result | 32 MiB | Product limit (not configurable) |
| Objects in one pack | 1,000,000 | Default (not configurable yet) |
| Longest delta chain in a pushed pack | 50, git's own `pack.depth` default | Default (not configurable yet). A client that raised `pack.depth` can be refused |
| Ref updates in one push request | 10,000 | Default |
| Push options in one push | 100 | Default |

### Pack count

Every push adds a pack, and every fetch consults every live pack, so a
repository may hold at most `GIT_PACK_CAP` of its own live packs (default 16,
minimum 2). A push that would go over merges the smallest packs into one as it
commits, within a budget of `GIT_TAIL_MERGE_MAX_BYTES` (default 64 MiB) and
`GIT_TAIL_MERGE_MAX_OBJECTS` (default 500,000). When no merge within budget
makes room (for example while clones are reading the packs it would merge),
each ref gets "try the push again later" and a background merge is
scheduled; the retried push succeeds.

### Borrowed packs

A repository of a fork network also reads packs it borrows from other
members (no byte is copied): a fork its parent's, a pull request's base its
head's. Its view holds at most 32 packs, its own and borrowed, so it may
borrow at most 32 less `GIT_PACK_CAP` (16 by default). Past that, a
background job merges its oldest borrowed packs into one, at most 16 packs
and 500,000 objects (the rewrite budget) a run. Importing a pull request's
head from a fork, or the base tip into a fork's head branch, adds its packs
only when such merges (the one under way first) bring the view within the
cap even were no object shared between merged packs (a merged pack's size
is known once written). When even packs sharing every object they could
would not fit, it is refused: opening the pull request, or the write to the
head branch, answers 422 `view_full`, and a later revision of an open pull
request's head is not imported (the pull request keeps its last one). In
between (only shared objects would make room), the merge job is asked for
and the import waits for the real sizes: 409 `busy` (try again), or the
revision is imported once the merges are done; it is refused when the
merges leave nothing more to tell. A pack already merged counts as nothing
new: a later import naming it again reads it through the merged pack, and
borrows it again only once the merged pack has left the view (dropped by
the repository's collection). Each merged pack remembers at most the 256
packs most recently merged into it (merging it again moves them to the new
one, so a merge moves at most 256 for each pack it takes); an older one is
borrowed again when an import names it. A view over its cap all the same
(the budget lowered since) leaves the merge job failing, tried again in
case a collection drops packs.

A repository gives up its claim on a pack of the network as its retire job
drops the pack's row. The network is told at the end of that pass, at most
100 releases a pass and one call per network; a release it could not be
told is kept and told again on a pass 10 minutes later. A release removes
only a claim no newer than the repository knew of when it gave the pack
up, so one that lands late or twice never undoes a pull request's import
that claimed the pack again since, even one made after the network's object
was restored to an earlier point in time (claims are ordered by the
object's clock as well as by what it stored). An import whose repository gave up any
claim between sharing its packs and adopting them shares them again first;
more than 3 times within one request, it answers 409 `busy`. A repository
restored to an earlier point in time claims again every pack its restored
registry holds: taking its new restore generation (at once when the
restore asks for it, otherwise with its first write) queues a job that
does so on the object's next alarm, a network at a time, asking a network
it cannot reach again after 30 seconds, doubling to an hour. No release it
recorded after the restore point removes those claims. Until the job has
run, a restored row whose claim such a release removed has none: the
network keeps the pack's bytes for 30 days after condemning it (which came
after the restore point), and deletes them only if the job has still not
run by then. Likewise a release recorded before a member says its view
holds a pack (to a collection, or refusing a deletion) leaves the claim
the network makes again for it.

### Push policy

- **Ref names** follow git's own rules (`git check-ref-format`), must start
  with `refs/`, must be valid UTF-8, and are at most 1,024 bytes. git itself
  accepts any bytes in ref names; Fyrden refuses names that are not UTF-8 with
  "ref name must be valid UTF-8", because every other surface (REST, MCP,
  webhooks, the web UI) is JSON.
- **A ref named twice** in one push is refused.
- **Hidden refs:** `refs/pull/` is managed by Fyrden; pushes cannot create,
  update or delete refs there.
- **The default branch** cannot be deleted by a push.
- **Branches** (`refs/heads/...`) must point to commits.
- **Object checks** are git's `fsck` checks with git's own severities, on
  every pushed object, for `git push`, `fyrden push --chunked` and imports
  alike. Anything `git fsck` reports as an error refuses the push, and so do
  the warnings that protect people who clone the repository: `.git` in a tree
  (including NTFS and HFS+ look-alikes), `.` or `..` entries, names
  containing `/`, empty names, and entries naming the null object id. The
  `.gitmodules` and `.gitattributes` errors refuse too (a symlinked
  `.gitmodules`, unsafe submodule names, paths and URLs, oversized
  `.gitattributes`). Other warnings and info-level findings are accepted and
  shown to the client as warnings: zero-padded tree modes, unusual file
  modes, very long names, a NUL byte in a commit message, tags without a
  tagger or with an unusual name. Many long-lived repositories have these in
  their history; GitLab, for example, turns off the zero-padded mode check
  on push for that reason
  ([Gitaly consistency checks](https://docs.gitlab.com/administration/gitaly/consistency_checks/)).
  git's own `receive.fsckObjects` is stricter (it refuses every warning
  unless `receive.fsck.<id>` relaxes it), and stock git checks nothing on
  receive by default.
- **SHA-1 collision attacks** are detected (SHA-1DC, as in git and on
  GitHub); a colliding object refuses the push.
- **Connectivity:** every object a new ref needs must be in the push or
  already in the repository, with the right type.
- **Shallow pushes** (from a shallow clone, when the push depends on the
  shallow boundary) are refused as a whole.
- **Atomic pushes** (`git push --atomic`) apply every ref or none. Without
  `--atomic`, each ref succeeds or fails on its own.
- **Compare-and-swap:** a ref whose current value is not the one the client
  expected (for example `--force-with-lease`) fails with git's reason.

## Fetch and clone

- **Protocol v2 only** for fetch and clone (git 2.26 or later, the default
  since 2.26). A protocol v0 or v1 fetch gets an error naming protocol v2.
  Pushes use git's receive-pack, as protocol v2 defines no push.
- **Shallow clones and fetches:** `--depth`, `--shallow-since`,
  `--shallow-exclude` and `--deepen` are supported.
- **Thin packs** are sent to clients that ask for them on incremental fetches.
- **Not supported:** partial clone (`--filter`), `wait-for-done`,
  `server-option`, `object-info`, `bundle-uri` and packfile URIs. Dumb HTTP is
  not served.
- **Request size:** a fetch request (the wants and haves) may be at most
  16 MiB after decompression, with at most 100,000 wants and 100,000 haves.

### Free and Paid serving

The deployment's plan is the `FYRDEN_PLAN` variable that
`fyrden deploy --plan free|paid` sets.

| | Free (or unset) | Paid |
|---|---|---|
| Response framing | The repository's Durable Object writes a side-band framed copy of the pack set to R2 once; the Worker then streams it with native pipes | The Worker frames the pack while it streams it |
| Why | A Free Worker gets about 10 ms of CPU per request ([platform limit](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)). **Measured** on Workers Free (2026-10-10): native pipes cost 1 to 4 ms of CPU for 100 MiB to 1 GiB, while framing in Worker code costs 240 to 353 ms per 100 MiB, and a framed 1 GiB clone was stopped for CPU after 632 MB with the response already started | Framing measured at about 2.4 to 3.7 ms of CPU per MiB (Free account, 2026-10-10), well within Paid's 30 s default |

On both plans, a clone that cannot be served from the stored packs as they are
(the packs hold objects the refs no longer reach, for example) gets a pack
regenerated by the Durable Object and stored in R2 before the Worker streams
it.

### Subrequest budgets

Each Worker request and each Durable Object invocation has a budget of calls
([platform limit](https://developers.cloudflare.com/workers/platform/limits/#subrequests)):

| Budget | Free | Paid |
|---|---|---|
| Calls to internal services: R2, D1, Durable Objects, Queues | 1,000 per invocation. **Measured** (2026-10-10): R2 binding calls, D1 queries and Durable Object calls share these 1,000, from a Worker and from a Durable Object. **Measured** (2026-10-26): a queue consumer and a Durable Object alarm each ran 1,000 D1 queries, and the 1,001st was refused (`Too many API requests by single Worker invocation`); in the consumer, 999 D1 queries and a Durable Object call fit | Cloudflare's pages disagree: 10,000 internal calls by default, configurable to 10,000,000 (Workers limits), but 1,000 D1 queries per invocation (D1 limits). Not measured |
| Outbound `fetch` and Cache API calls | 50 per invocation. **Measured** (2026-10-10): the Cache API and `fetch` share these 50 | 10,000 for `fetch`; 1,000 Cache API calls per request (platform limits; not measured) |

D1's limits page gives Free 50 D1 queries per invocation. That did not
hold in any invocation measured above: on Free, D1 queries count against the
1,000 internal calls. A `db.batch()` counts as one call however many
statements it holds.

**Measured** (2026-10-10): every request into a Durable Object starts with a
fresh budget, so the repository object's work does not use the Worker's.

Sliced work is admitted against the deployment's per-invocation budget of
internal calls: 1,000 on Free, which cannot be raised, and 1,000 on Paid
unless `fyrden deploy --plan paid --internal-calls N` (N from 1,000 to
10,000,000) sets `FYRDEN_INTERNAL_CALLS`, plus `limits.subrequests` when N
is past Paid's default 10,000. Raise it only after measuring D1 queries per
invocation on the Paid account. A budget set too high fails calls in the
middle of a slice. One set too low only costs more invocations. Pass the
flag on every deploy: the generated config keeps nothing from the last one.
From that budget:

- A job queue (a repository's or a network's) starts no slice once the
  invocation has made more than the budget less 200 calls (800 on Free),
  the most one slice makes.
- The events and effects consumers share the budget less 100 among a
  batch's messages (900 on Free); a message past it waits for the next
  invocation, and a message alone always runs.
- An archive slice reads at most the budget less 100 less the calls already
  made.

**Measured** (2026-10-26, Free): from the queue consumer, sequential D1
queries took about 190 ms each (1,000 in 184 to 194 s of wall time, 476 to
514 ms of CPU, not stopped for CPU), against about 9 ms each from a Durable
Object alarm (1,000 in 9.1 s, 404 ms of CPU). A consumer's D1 work should be
batched, not sequential.

What this means for clones:

- Pack bytes are read from R2 in large ranges (whole packs when serving them
  as they are), so a clone makes few R2 calls. Counted in local integration
  tests (2026-10-11), cloning a one-pack repository took: on Free, 1 R2 read in
  the Worker and 3 R2 calls in the Durable Object the first time, then 1 and 1;
  on Paid, 1 and 1; a regenerated pack on Free, 1 and 4 plus 2 Cache API calls.
- A repository may have at most 16 own live packs (the pack-count cap), which
  bounds the R2 calls of a clone served as stored.
- The Durable Object caches pack blocks in the Cache API for reads that need
  random access. It stops calling the Cache API once the invocation (a
  request or an alarm, with every indexing phase or job it runs) has made 40
  external calls (default), Cache API and outbound `fetch` together, under
  Free's 50. A Cache API call that fails is treated as a miss.
- Background jobs start no new slice once the invocation has made the
  budget less 200 calls to R2, D1 and Durable Objects (800 on Free); the
  alarm continues them in a new invocation.
- A cold clone of a 1 GB repository has not been measured yet on Paid.

### Durable Object CPU

A Durable Object gets 30 s of CPU per request and per alarm by default
([platform limit](https://developers.cloudflare.com/durable-objects/platform/limits/)).
**Measured** on Workers Free (2026-10-10): an alarm that used 27.0 s of CPU
completed, one at 32.5 s was reset and retried. A reset loses the writes of
that invocation, so Fyrden's long work is sliced and saves its place:

- Push indexing runs for up to `GIT_PUSH_INDEX_BUDGET_MS` (default 10 s) in
  each request, then continues in the object's alarm. The Worker waits (no
  CPU) and keeps the client's connection alive.
- Repack and garbage collection slices stop after 20 s, 200,000 objects,
  256 MiB written or 500 R2 calls (defaults), whichever comes first.
- The five-minute maintenance cron (archiving the directory's audit log,
  expiring repositories, advancing deletions and transfers, reaping keys)
  runs in a Durable Object of its own, which the cron trigger calls: a
  cron trigger gets 10 ms of CPU on Workers Free
  ([platform limit](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)),
  and the run took 14 to 80 ms (measured on Free, 2026-10-22). A run asked
  for while one is under way joins it.

Not measured yet: the CPU needed to parse the largest packs, as the first
parsing pass of one pack runs in one invocation.

Each Durable Object has 128 MB of memory
([platform limit](https://developers.cloudflare.com/workers/platform/limits/#memory));
Fyrden's git operations in one repository share a 72 MiB pool (default) and
wait for room rather than exceed it. A fetch plan and a push's indexing
phase first wait for their share, holding nothing (25 MiB plus the packs'
indexes, up to the whole pool, and 33 MiB, with the default limits), then
reserve from it: a reservation that fits what is left of their share is
granted at once. What they need past it (tables that grow with the
repository, the objects a push resolves) comes from the pool ahead of work
not yet started, and can wait for other work, so concurrent ones that both
need more than their share can still wait on each other. In a small
repository two shares of either kind fit in the pool at once; the rest wait
their turn. A wait past 60 s fails: a fetch then answers that the repository
is busy and to try again. Besides the pool, a repository keeps pack blocks
(16 MiB) and pack indexes (8 MiB) in memory between requests, so finding an
object in a pack it read recently reads nothing from R2; an index over 2 MiB
(a pack of about 75,000 objects) is read by ranges instead. Index reads in
flight count against the 8 MiB too: when they fill it, further index reads
wait for them to finish.

## Chunked upload sessions

The `uploads.*` operations (and `fyrden push --chunked`) take a pack in parts:

| Limit | Value | Variable |
|---|---|---|
| Part size (every part but the last) | 16 MiB (default; at least 5 MiB, and below the request body limit) | `GIT_UPLOAD_PART_BYTES` |
| Parts per session | 10,000 ([R2 platform limit](https://developers.cloudflare.com/r2/objects/upload-objects/)) | |
| Largest pack per session | 8 GiB (default) | `GIT_UPLOAD_MAX_BYTES` |
| Ref updates per session | 1 to 1,000 | |
| How long one `complete` call waits for indexing before answering `indexing` | 20 s (default); call again | `GIT_UPLOAD_COMPLETE_WAIT_MS` |
| Session lifetime | An upload not committed within 24 hours (default) is removed with its parts | |

Only the token that started a session can complete it, and the push is
re-authorized when it commits. A part can be uploaded again; the last upload
wins. One request at a time uploads a given part: another upload of the same
part meanwhile is refused with `part_in_progress` (HTTP 409, `Retry-After`),
and `complete` waits (`parts_in_progress`) until no part is being uploaded. A
request that stalls for 10 minutes (default) loses the part to the next
upload; its own late answer is then refused (`part_superseded`) and the part
must be uploaded again. `fyrden push --chunked` retries both.

## Server-side import

An import copies a repository from another git server into an empty Fyrden
repository:

- The source URL must be `https://`, at most 2,048 characters, without
  credentials, query or fragment. Its host must resolve to public addresses
  only (checked on every request; redirects are refused), and must not be the
  deployment itself.
- **Own hosts:** the deployment's own hostnames are refused, so an import
  cannot loop back through Fyrden. They are the host the request arrived on;
  on `workers.dev`, both Fyrden Workers on the same account subdomain; and any
  extra hostnames in `FYRDEN_OWN_HOSTS` (comma separated). Set it to every
  custom domain routed to either Worker.
- The source must speak git protocol v2.
- Only `refs/heads/*` and `refs/tags/*` are imported, at most 10,000 refs.
  Refs whose names are invalid or not UTF-8 are skipped and listed in the
  import's report.
- At most `GIT_IMPORT_MAX_BYTES` (default 4 GiB) and `GIT_IMPORT_MAX_MS`
  (default 10 minutes) of fetching per import.
- **A slow source is stopped early.** The fetch runs in the repository's
  Durable Object, which stays active, and is billed for its duration, while
  it waits on the source ([platform pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/):
  pending I/O keeps an object in memory, and it incurs duration charges
  during that time), so a
  source that stalls or trickles does not hold it for the
  whole 10 minutes (Proposed defaults, checked every 5 seconds):

  | Limit | Default | Variable |
  |---|---|---|
  | Connecting (name lookups included) and listing the branches and tags | 30 s | `GIT_IMPORT_DISCOVERY_MS` |
  | Nothing received while the pack streams (keepalives and progress messages count) | 60 s (git's upload-pack sends a keepalive every 5 s by default while it prepares the pack) | `GIT_IMPORT_IDLE_MS` |
  | Pack throughput, over every minute after the first two (pack data only: progress messages and keepalives do not count) | at least 16 KiB/s (a 4 GiB import needs about 7 MiB/s to finish in time) | `GIT_IMPORT_MIN_BYTES_PER_SECOND` |

  A pack of B bytes therefore holds the object for at most about
  3 minutes + B / 16 KiB/s, and never past `GIT_IMPORT_MAX_MS` (storing the
  pack included). A source stopped this way fails the import at once,
  without a retry, with the error `the source took too long: ...` naming the
  limit, even when the rest of the pack arrived while it was being stored;
  whatever was stored is removed. Once the fetch is over, stopped or not,
  any response the source left open is cancelled. The transfer stays in the
  Durable Object because a Free Worker serving a request gets about 10 ms
  of CPU per invocation (a queue consumer gets 30 s by default, on Free as
  on Paid: [Queues limits](https://developers.cloudflare.com/queues/platform/limits/);
  moving the transfer to one has not been examined): the pack
  arrives in side-band frames that Worker code must take apart, and framing
  in Worker code was measured at 2.4 to 3.7 ms of CPU per MiB (see Free and
  Paid serving; taking frames apart is assumed to cost about as much,
  unverified).
- The imported pack is checked like any push.

## Maintenance and retention

Repack, garbage collection and cleanup run in each repository's Durable Object
alarm. These periods are defaults and are not configurable in this version:

| What | When it is deleted |
|---|---|
| Packs replaced by a repack or collection | 30 days after they were replaced, and never while a clone that started before still reads them |
| Unreachable objects (moved to a garbage pack by collection; a pull request's recorded base, `base.sha`, counts as reachable) | Condemned 1 day after the garbage pack was last touched, then deleted after the 30-day retention |
| Reflog entries | After 90 days, by a pass that commits schedule (at most daily). Objects reachable only from the reflog are kept until then |
| Uncommitted uploads and their stored bytes | 24 hours after the upload started |
| Stored fetch responses (regenerated or framed packs) | 1 hour after the last clone that read them |
| Outputs of an interrupted repack | 24 hours |
| An event's stored data (a change too large for one queue message keeps its data in the repository, for consumers to fetch) | 7 days after the event was sent; never while it waits to be sent |

A repack that replaces packs a clone is reading waits up to 1 hour for that
clone before it switches; the old packs stay readable either way.

A fork network (a repository and its forks) is also collected as a whole,
daily while it has more than one member, in the network's own Durable Object
alarm. Each member reports which of the network's shared packs it still
reads; a shared pack none reads is deleted once every member has
acknowledged it and the 30-day retention has passed. Files under the
network's pack prefix older than 1 day that no member's registry names are
deleted: the members are asked a page of 100 files at a time, and no more
once every file of the page is accounted for. Each slice of this work makes
at most 100 calls to members, R2 and D1 (Proposed) and saves its place, and
an alarm starts no slice past the call budget less 200 (800 on Free; see Subrequest budgets), so a network with many members is
collected over as many alarms as it needs. A collection due while a fork is
being created waits for it: it runs as soon as the fork is published or
abandoned, and a fork still unfinished after 1 hour is taken as abandoned
and removed. While a collection asks the members what they read, creating
a fork, detaching, and a pull request from a fork wait for it up to 10
seconds, then answer `network_busy` (retry later); a collection that fails
for good stops holding them up and runs again a day later.

## Repository deletion

`DELETE /repos/{owner}/{repo}` and the bulk `POST /user/repos/delete` start a
deletion that finishes in the background:

| What | Value |
|---|---|
| Names in one bulk delete | 1 to 100 |
| Deletions one request finishes itself | The one it deletes; 3 for a bulk delete |
| The rest | Advanced by the cron every 5 minutes, 10 per run, oldest first; one that is waiting goes to the back |
| Pushes, ref and setting changes | Refused as soon as the deletion starts |
| Found or read under any name | Not after about 30 seconds (an isolate that resolved it before may serve it until then) |
| The name | Taken until the deletion is `deleted`; free afterwards. The id is never reused |
| Audit records | Archived to R2 before anything is erased; an R2 outage makes the deletion wait |
| A clone or fork in progress | The erase waits for its read lease: 10 minutes, renewed while it reads |
| A push admitted before the deletion | The erase waits up to 15 minutes for it to store its body; a body stored later is deleted by the push itself |
| Forks | Keep the packs they borrowed; the network deletes a pack once no member claims it |
| Webhook deliveries, their attempts and bodies, the bodies' payload records, queued effects, search projections, and the directory's copies of its watchers and thread preferences | Deleted before the repository's storage, up to 7 pages a call (500 effects, 200 deliveries or payload records, 500 rows of each search projection table, 500 watch and 500 thread preferences, or 1,000 bodies a page); none are made once the deletion's tombstone is in the read model. A webhook effect of the repository that was claimed (its deliveries being made, or made) holds the cleanups until 15 minutes after it ended, a queue consumer invocation's wall-time limit ([platform limit](https://developers.cloudflare.com/queues/platform/limits/)), so no invocation that claimed it is still storing a body when the bodies are deleted; its pending webhook effects are ended first, 500 a page (`effects.invalidated`), and one claimed at the time is waited for until it ends. A repository whose webhooks made no deliveries in the 15 minutes before its deletion does not wait (all Proposed) |
| Incomplete multipart uploads of interrupted maintenance | Left to R2, which aborts them after 7 days |

A deletion that keeps failing shows `attempts` and `last_error` in the
directory's `repo_deletions` row.

## Browsing history

Branches, tags, commits, comparisons and files (`/repos/{owner}/{repo}/branches`,
`/tags`, `/commits`, `/compare/{base}...{head}`, `/contents`, `/readme`,
`/git/trees`, `/raw`) start from a branch, a tag or a full commit SHA of the
repository itself; a commit that only another repository of the same fork
network has is not found.

| What | Value |
|---|---|
| Page size | 1 to 100, default 30 |
| Commits one history page examines | 2,000, and about 400 R2 reads for the walk; with `path`, a page can hold fewer commits than asked (even none) and still have a next one |
| R2 reads one browse request makes | 800 at most (Free allows 1,000 calls per invocation); a history page then ends early, anything else answers `too_expensive` |
| Commit text in one answer | 8 MiB; a history page then ends early, anything else answers `too_large` |
| History order | Newest first by corrected commit date, then commit id: what `git log` shows, unless commit dates go backwards or are equal |
| Tags | A tag of a tree or blob is not listed; a page can be short (even empty) and still have a next one |
| Branches waiting in a history cursor | 256; a wider history answers `history_too_wide` |
| Commits a comparison counts on each side | 10,000; more answers `comparison_too_large` |
| Commits a comparison lists | The newest 100, oldest first |
| Commit text | Decoded as the commit's `encoding` header says (UTF-8 without one, or for an encoding the runtime does not know) |
| Directory entries per page (`/contents`) | 1 to 1,000, default 1,000 |
| File content in a JSON answer | 1 MiB; a larger file has `encoding: none` and is read through its `download_url` |
| Raw file (`/raw/{path}`) | 24 MiB; larger answers `too_large` (clone the repository instead) |
| Recursive tree listing (`/git/trees/{ref}?recursive=1`) | 10,000 entries; more, more trees than one request may read, or directories nested so that their trees together pass 32 MiB, is `truncated` |
| `/git/trees/{tree_sha}` | Takes a branch, a tag or a commit SHA; a bare tree SHA is not found |
| Names that are not valid UTF-8 | Shown with replacement characters; such a file cannot be asked for by path (clone the repository) |
| A directory page's cursor | Valid for that version of the directory; after the branch moves it answers `cursor_stale` |

## Archives

`GET /repos/{owner}/{repo}/tarball[/{ref}]` and `/zipball[/{ref}]` serve a
commit's files under `<owner>-<repo>-<short id>/`; `GET
/repos/{owner}/{repo}/archives/{format}` (REST and MCP) prepares one and
links it. The repository's object builds an archive in slices into R2 and
keeps it a week.

| What | Value |
|---|---|
| File content in one archive | 1 GiB; more fails with `archive_failed` (clone instead) |
| One file | 24 MiB; a symbolic link's target, 64 KiB |
| Zip entries | 65,535 (no ZIP64); use tar.gz past that |
| Directory depth | A path's directories, with their names, fit in 1 MiB of build state (about 2,500 levels of 255-byte names); deeper fails with `archive_failed` |
| Building | 8 MiB encoded or 5,000 entries per slice (a file that would take a slice past 8 MiB starts the next, alone if it is larger), at most 300 slices (a commit with very many small files fails: clone it); a file of 1 MiB or more has its bytes reserved while it is compressed, and waits for them; a request builds for up to 5 seconds, then answers 202 with `Retry-After: 5` until it is ready |
| Bookkeeping | A zip's central directory records wait for its last slice in rows of up to 1 MiB of them (about one a slice), written once and deleted with the last slice: rows written grow with slices, not files (they count toward Workers Free's 100,000 a day) |
| Kept | 7 days, then deleted when the repository next builds one (not while a download that started in the last hour may still read it); deleted with the repository |
| Dates | tar holds dates up to 2242, zip 1980 to 2107; later or earlier commit dates are written as the nearest one |
| Zip names | Flagged UTF-8 when they are; other bytes are written as they are, without the flag (as git does) |
| tar.gz | Several gzip members (any gzip reader reads them as one stream; a file of 1 MiB or more is one of its own); pax headers for long names; the commit id in a pax global header, as `git archive` writes |
| Downloads | `ETag` per commit and format; a matching `If-None-Match` answers 304 without reading the archive (raw files likewise, by blob) |

## File writes

`PUT`/`DELETE /repos/{owner}/{repo}/contents/{path}` and
`POST /repos/{owner}/{repo}/file-commits` make one commit on a branch. The
repository's object builds it and commits it through the push path: the pack
is checked like a pushed one, the token is checked again just before the
branch moves, and the branch moves only from the head the commit was built on.

| What | Value |
|---|---|
| Files one write changes | 1 to 100 |
| Content one write carries | 4 MiB (all files together), checked before it is decoded |
| Commit message | 64 KiB |
| Branch | Must exist; an empty repository takes a first commit on its default branch |
| Identity | Committer: the platform, `Fyrden <noreply@host>` (it signs). Author: the agent acting, else the caller, as `<handle> <id@users.noreply.host>`; `author` may name someone else. An agent acting for a user (a delegated token) adds `Co-authored-by: <user>` to the message, unless it already names the user; an agent with its own token acts for no one and adds none. Trailers are not authenticated: the audit log records who acted for whom. Repositories generated from a template take the same identity |
| Branch moved meanwhile | 409 `head_moved`; read again and retry |
| File changed meanwhile (`sha` given) | 409 `sha_mismatch` |
| Token revoked during the write | 403 `token_revoked`; nothing is committed |
| Indexing wait | 4 steps of up to 5 seconds; a busier repository answers 409 `busy` |
| Directories a write reads | About 300 R2 reads' worth; deeper writes answer `too_expensive` |
| A directory a write changes | 1 MiB as a tree object (about 25,000 entries), 4 MiB of trees in all; larger answers `too_expensive` (push instead); memory for them is reserved, or the write answers `busy` |
| Request body (REST and MCP) | 8 MiB; larger answers 413 `body_too_large` before it is read |
| Retrying a write | Send an `Idempotency-Key` (see [Idempotent requests](#idempotent-requests)): a retry gets the first answer and makes no second commit |
| Signature | Signed with the platform key (see [Commit signing](#commit-signing)) |

## Repository expiry

A repository may carry `expires_at` (Unix milliseconds), set when it is
created (also by fork or generation) or by an update, and cleared with
`null`. The cron, every 5 minutes, marks expired repositories for deletion
and advances their deletions in the same run; they go through the ordinary
deletion, audited as `repo.expire` with no actor.

| What | Value |
|---|---|
| Earliest | Any time in the future; a past time answers 422 `invalid_expiry` |
| Latest | One year ahead |
| Repositories marked per cron run | 50; the rest in later runs |
| Deletions advanced per cron run | 10 (as for any deletion) |

## Quotas

Each account (a user or an organization) has two limits, set per account by
an instance administrator (`PUT /admin/accounts/{account}/quota`) or else the
instance defaults below; `GET /user/quota` and `GET /orgs/{org}/quota` show
them and their use.

| What | Value |
|---|---|
| Active repositories | 1,000 by default (`QUOTA_MAX_REPOS`). Create, organization create, fork and generate past it answer 403 `quota_exceeded`; the check holds against concurrent creates. Repositories being deleted do not count |
| Storage | 1 GiB by default (`QUOTA_MAX_STORAGE_BYTES`): the bytes the account's repositories' pushes stored, as received (pack and commands). Forks count nothing until pushed to; repacking does not change it; a deleted repository's bytes are free once its deletion finishes |
| Before a push is stored | Its `Content-Length` is reserved, or, without one, as much as is free (up to the body limit); a push larger than the reservation is refused with a message git shows. A chunked upload reserves its declared size |
| At the commit | The push's stored bytes are held for it; one that does not fit (the limit was lowered, or a write the repository makes itself: file writes, imports, generation) is refused, every ref `ng`, nothing changed. Once committed, the bytes become the repository's usage |
| A push that commits nothing | What it reserved or held is free again |
| Holds | A reservation lasts the push's longest wait plus 15 minutes (a chunked upload's session plus an hour), a commit's hold 30 minutes; a lapsed one counts nothing. A commit's confirmation is owed by its repository until the account takes it (counted once): one that fails is told again every minute, for up to six days (then given up, uncounted: the account remembers the ones it took for seven) |
| Forks | A fork that loses the last slot to a concurrent create is deleted again |
| An agent's repositories | Besides the account's quota, an agent acting for a user may have created at most 100 active repositories (`QUOTA_AGENT_MAX_REPOS`); past it, 403 `quota_exceeded`, held against concurrent creates |

## Repository transfer

`POST /repos/{owner}/{repo}/transfer` moves a repository to the caller or to
an organization it may create repositories in. It runs as a resumable job:
the repository stops taking changes, the directory moves its owner and name,
the old account hands over its collaborators and storage, and the
repository's object takes its new owner. The request usually sees it land;
the cron finishes any it does not.

| What | Value |
|---|---|
| Moves with it | History, refs, rulesets, stars, forks' parent link, collaborators, storage usage |
| Stays behind | The old organization's team grants, and its teams' review requests (their members' items settled by a job) |
| The old path | Redirects to the new one (for the API, clone, fetch and push), until the old account uses the name again |
| While it moves | Pushes, file writes, renames, settings, rulesets and deletion are refused (409 `repo_transferring`, or "being transferred" to git); reads go on |
| Refused | 409 `name_taken`, 403 `quota_exceeded` (repositories or storage), 422 `same_owner`, 409 `transfer_in_progress` (another transfer or a deletion is under way, or the owner changed since the request was authorized), 409 `repo_generating` (still being generated from a template), 422 `too_many_collaborators` (the new account's members and the repository's collaborators would exceed one access list's 10,000 entries); a refused transfer leaves the repository as it was |
| Storage of an upload committing as it moves | Not counted (its confirmation reaches the old account, which no longer counts the repository) |
| Admission checks | The new account's repository count is enforced when the directory moves the repository. Just before the move, the new account makes room for it, held until the transfer lands or is called off: its storage (and, charged to each, the uploads whose confirmations it still owes, until the new account takes them) and its collaborators, counted against later membership changes. Concurrent transfers and members added meanwhile cannot take the account past either limit |
| One runner at a time | A runner holds a transfer for 60 seconds; one that dies frees it after that |
| Caches | Other Workers may resolve the old path to the old owner for up to 30 seconds; access is decided by the repository, which knows its owner, and changes authorized for the old owner are refused |
| Read model | Events from before the transfer are refused once it lands (a new owner generation) |
| Restore | A repository object restored from before a transfer or rename takes, with its new epoch, the owner and name the directory names now, in an owner generation no older than the read model's; if the directory has a transfer under way, the object rejoins it, frozen, and the transfer lands it. An account object (an organization's or a user's) restored from before a user deletion retired its principals forgets them again on its own, once it takes its new epoch: its alarm reads the lifecycle of the principals it holds, a page at a time, and removes the memberships, team memberships and collaborator grants of those being deleted or deleted, keeping an organization's last owner (an administrator hands it over). One restored from before its deletion (under way or finished) is frozen again and answers as deleted, and its deletion starts over from the beginning, once a restore, every step and cleanup run again (an earlier run's late progress is ignored). An object takes its epoch before any call or alarm does any work, once an instance: while the directory cannot be read, its first calls fail and its alarm waits a minute (Proposed) and tries again |
| Transfers one cron run finishes | 10 |

## Agents and delegation

Agents are principals owned by a user or an organization (`POST /agents`).
An agent acts with its own tokens (`POST /agents/{agent}/tokens`) and its
own collaborator roles, or for a user under a delegation grant
(`POST /grants`): it exchanges its own token for a delegated one at
`POST /oauth/token` (RFC 8693 token exchange, `grant_id` names the grant).
A delegated token's principal is the user; its act chain names the agents
acting, the current one first, and audit rows carry it.

| What | Value |
|---|---|
| An agent's rights | Its own (or the user's, under a grant), capped by its owner's: an organization's agent reaches only the organization's repositories |
| A repository's `permissions` | `GET /repos/{owner}/{repo}` answers GitHub's `permissions` (`admin`, `maintain`, `push`, `triage`, `pull`) for the caller's role there, never above an acting agent's owner's; a public repository's `pull` holds for any reader. They say what the role allows: the token's scopes and repositories are decided by each operation, as GitHub's are |
| A repository's `owner_type` | Fyrden's (GitHub's `owner.type`): `User` or `Organization`, on a repository read through the directory (`GET /repos/{owner}/{repo}` and listings); absent from one just created or forked. A transferred repository may be reported with its former owner's kind for as long as its former owner (30 s, an isolate's cache) |
| A grant | Scopes (at least one), optionally repositories, an expiry of up to 365 days; never wider, nor longer-lived, than the token making it |
| Passing down | An agent holding a user's grant may pass a narrower one (scopes, repositories, expiry) to another agent of its owner; one hop at most (depth 2) |
| Delegated token | Type `oat`, up to 1 hour, and never past any grant of its chain or the agent's own token; scopes and repositories within the grant and the agent's token; for the REST API unless `resource` asks for the MCP server |
| Revocation | Revoking a grant revokes the grants passed down from it; tokens under them, an agent's token its owner revokes (`DELETE /agents/{agent}/tokens/{token_id}`; `GET /agents/{agent}/tokens` lists them) with the delegated tokens exchanged for it and the git tokens minted from those, and an agent's tokens once it (or its owner) is disabled, stop at once for writes and within 30 seconds for reads |
| Suspension | `PUT /users/{username}/suspended` (an optional `reason`, at most 200 characters) and `DELETE` the same, as GitHub Enterprise's (204, no body); instance administrators only, never yourself, never the last active administrator (decided in the change's own statement, so two administrators suspending each other leave one). A suspended user cannot sign in; their sessions, OAuth access and refresh tokens, unanswered authorization requests and unused codes are revoked for good; their personal access tokens, git tokens and delegations, and those of the agents they own, stop (at once for writes, within 30 seconds for reads) and work again once unsuspended. A sign-in, a consent, a passkey registration, or the making of a token, agent, delegation grant or signing key that the user's own request began before the suspension grants nothing, even once the user is unsuspended (an agent's request made with its own token, which the suspension keeps, may land once its owner is unsuspended, as one made then could). No grant of the suspended user's is passed down while they are suspended. A suspended reviewer's approvals stay listed but stop counting toward a merge at once, and count again once unsuspended. Other work already authorized may finish (a push holds its authorization for up to a minute). Their repositories stay available to their collaborators. Each suspension and unsuspension is recorded with its generation (`principal_lifecycle`) and audited (`user.suspend`, `user.unsuspend`) |
| Owner handoff | `PUT /admin/organizations/{org}/owners/{username}` (instance administrators; 204, no body), as GitHub Enterprise's `ghe-org-admin-promote`: makes a user an owner of an organization, a member or not, whatever its owners say (for one whose owners can no longer act). Making an owner an owner changes nothing. Never a user who is suspended or being deleted (refused 404 `user_not_found`); a deletion that begins after that check is refused again in the organization's object, a suspension is not. Audited `org.owner_handoff` |
| User deletion | `DELETE /admin/users/{username}` (instance administrators; never yourself, nor the last active administrator; MCP `delete_user`), as GitHub Enterprise's, with the user's repositories: answered 202 with where the deletion is (`state`, `step`, `blocked`), where GitHub Enterprise answers 204 and works at once. Asked again it answers the same, by the released handle while it is held and by the user's id at any time (a deleted user's handle is their id). At once, in one transaction: the user and the agents they own can no longer authenticate or issue anything (writes refused at once, reads within the token cache's 30 seconds); every credential of theirs is revoked or removed (tokens of every type, sessions, OAuth refresh tokens, unanswered authorization requests and codes, passkeys, signing keys, grants from or to them); their handles are released and held for 90 days (no user, organization or agent takes one until then, whatever its case); an isolate that cached a resolution of their repositories may serve it for up to 30 seconds. Then a job (its state in the directory, advanced by a Durable Object's alarm a bounded slice at a time; Proposed shares: 50 repositories, 50 account calls of 100 principals and 500 rows each, 500 stars, 25 feeds a run): their repositories go to repository deletion (one being transferred away waits for its transfer); every account recorded before the deletion began removes their memberships, team memberships and collaborator grants (an organization they solely own blocks the job, `blocked: sole_owner:<organization id>`, until an administrator makes someone its owner with `PUT /admin/organizations/{org}/owners/{username}`, which, like any promotion to owner, sets it going again at once, unless a run already under way saves its wait after that: it then tries again within the hour); their stars go; their feeds are retired; and once no repository is theirs but those whose deletion is done (one reopened by a restore holds it back), they are `deleted` (`step: done`). What they made in others' repositories stays (comments, reviews, commits, review requests, assignments), shown as `ghost`; a review request of theirs gives up its place once a new request would pass the 15. A failed run backs off from a minute to an hour; a cron trigger of its own (`4-59/5 * * * *`) re-arms a due job whose alarm was lost, one a run, in turn. `GET /healthz` reports `checks.deletions` as not ok, without failing the health check, while a job is blocked, one's last run failed, or one has been due and not run for an hour (Proposed). Audited `user.delete` (with how many principals it retires: the user and their agents) and `user.deleted`. A user may own any number of agents: the deletion's own record names only the user's handle, each agent's being held by its own reservation |
| Delegated tokens may not | Make or revoke grants, mint tokens (but a git token for themselves), change who has access (collaborators, team repositories), call user-only operations (transfer, stars), or manage signing keys (they would be the user's) |
| Repositories an agent creates | Acting for a user under a grant with `repos:create` (create and fork): the user's, within every acting agent's owner's rights; each expires after 7 days (`AGENT_REPO_TTL_DAYS`) unless `expires_at` says when (at most a year: an agent may move it, only the user may clear it), and counts against the agent's own limit (see Quotas). An agent's own token, or a token limited to repositories (by its grant or the agent's token; it could not reach the new one), creates none |
| An agent's own token | Never wider than the token that minted it (scopes and repositories) |
| Token endpoint | Bodies up to 16 KiB; rate limited per client address |
| Rulesets | Rules for `agent` actors apply to an agent acting for a user |
| Git tokens for the caller | `POST /user/git-tokens` (MCP `create_git_token`): a `git` token for stock git, as the caller (a user, an agent, or an agent acting under a grant, keeping that grant and chain: revoking the grant stops it); `contents:write`, or `contents:read`, within the caller's scopes; 1 hour at most (`expires_in_minutes`), never past the caller's token. The only token minted over MCP |
| Not yet | Grants from organizations |

## OAuth authorization server

Fyrden is its own authorization server (OAuth 2.1, public clients with
PKCE), for MCP clients and other tools acting for a signed-in user.
Discovery: `/.well-known/oauth-authorization-server` (RFC 8414) and
`/.well-known/oauth-protected-resource/{mcp,api}` (RFC 9728), which a 401
from `/mcp` or `/api` names in its `WWW-Authenticate`.

| What | Value |
|---|---|
| Clients | Public only (`token_endpoint_auth_method: none`): known by a client ID metadata document (an `https` `client_id` URL with a path, fetched through the outbound URL policy, at most 5 KiB, naming itself, kept a day, a week if it cannot be fetched again), or registered at `POST /oauth/register` (RFC 7591); redirect URIs `https`, loopback `http`, or a private-use scheme, matched exactly (loopback with any port) |
| DPoP (RFC 9449) | A token request with a proof (ES256 or EdDSA) gets tokens bound to its key (`token_type: DPoP`), taken only with `Authorization: DPoP` and a fresh proof by that key (60 seconds either way; each proof once); `dpop_jkt` at authorization binds the code; a bound refresh family needs proofs by its key |
| Organization policy | `PATCH /orgs/{org}` `require_dpop`: the organization's agents' API tokens are taken only DPoP-bound (at once for writes, within 30 seconds for reads, like a revocation), and token exchange for them needs a proof (git tokens only where git itself uses them, since git cannot send a proof: smart HTTP and the chunked upload session `fyrden push --chunked` drives, `/api/repos/{owner}/{repo}/uploads`; elsewhere at the REST API, and at MCP, they are refused like any other) |
| Authorization | `GET /oauth/authorize`: code flow only, PKCE `S256` required, `resource` required (`{origin}/mcp` or `{origin}/api`), scopes are Fyrden permissions; the signed-in user consents on a Fyrden page; the answer must come from Fyrden's own origin |
| Codes | Single use, 60 seconds; redeemed again, the tokens they issued are revoked |
| Access tokens | Type `oat`, 1 hour (never past their family's end), accepted only at their resource (RFC 8707) |
| Refresh tokens | 30 days, single use, within a family of at most 90 days (then the user consents again): each use issues the next; a used one coming back revokes its whole family (refresh and access tokens); of concurrent uses exactly one wins |
| Revocation | `POST /oauth/revoke` (RFC 7009): a refresh token revokes its family, an access token itself |
| Requests | Bodies up to 16 KiB; token, registration and revocation rate limited per client address; authorization requests rate limited per user, with at most 20 waiting for an answer |
| Registrations | At most 1,000 an hour for the whole deployment; one never used within a day, or unused for 90 days, is pruned |
| Pruning | Expired access tokens, refresh tokens, sessions and answered or abandoned requests go a day after they expire (their audit rows stay) |
| Sessions | A `__Host-fyrden_session` cookie (HttpOnly, Secure, SameSite=Lax), 30 days |

## MCP server

`/mcp` serves MCP over stateless Streamable HTTP (protocol revision
2026-07-28): a tool per API operation (but those returning a credential, other
than a short-lived git token), and repository files as resources
(`fyrden://repos/{owner}/{repo}/files/{+path}` on the default branch,
`fyrden://repos/{owner}/{repo}/refs/{ref}/files/{+path}` at a branch, tag or
commit, a branch's slashes as `%2F`; not listed, a client names the file it
wants), and the caller's activity feed (`fyrden://feed/{principal id}`,
listed, read as `sync_feed` answers). Each request builds its own
server; each tool's JSON Schema is converted once per Worker isolate and
shared after that.

| What | Value |
|---|---|
| Tools | 77; `tools/list` answers about 161 KB |
| Browser requests | Only from the deployment's own hosts (`Origin`, against DNS rebinding): on `workers.dev`, both Fyrden Workers on the request's account subdomain; the hosts in `FYRDEN_OWN_HOSTS`; loopback. Native clients send no `Origin` |
| Request body | 8 MiB, as REST |
| CPU per request | **Measured** on Workers Free (2026-10-14, `wrangler tail`): `tools/list` 5 ms on a warm isolate with 63 tools (45 to 160 ms before tool schemas were converted once per isolate); `whoami` 32 ms and `resources/read` 16 ms (measured before that change) |
| Feed push | Where live hints are on (below), 2026-07-28's `subscriptions/listen` with the caller's own feed URI in `resourceSubscriptions` (`resources.subscribe` is offered then, and only on 2026-07-28: the 2025 revisions have no listen, and their subscriptions need a session). The request is validated as the MCP SDK serves it; the stream is Fyrden's own. It holds one live socket of the feed's object, opened before the acknowledgement, so a client that listens first and then reads the feed (`resources/read`, or `get_feed` from its cursor) is told of what changes after; each change the credential may read then sends `notifications/resources/updated` for the feed's URI, a hint to read again (what changed is not told; changes not yet sent fold into one). Each answered renewal sends one too (about every 5 minutes): changes whose access could not be decided are passed over, as for browser sockets, which read again on renewal. Any other URI is left out of the acknowledgement and never sent; with none left (or live hints off) the stream is acknowledged empty and ends. Same credentials, admission and caps as the live sockets (a session or the principal's own token; a delegated token is refused, `delegated_listing`, and so is a DPoP-bound one; 5 a credential and 20 a principal at once, browser sockets included; 60 opened a principal a day), and the token's write rate limit. A refusal is a JSON-RPC error whose `code` is the HTTP status and whose `data` is the problem (`status`, `code`, `retry_after`). The request's `id` is stamped on every message, so it is at most 256 bytes of JSON (400 `listen_id_too_long`). Messages are made only as the client reads, one at a time: a client that stops reading acknowledges nothing, so once 8 frames wait the socket's window is full and 2 minutes later its stream ends. Frames are acknowledged every 4 taken, within the socket's control budgets (2 a minute and 4 of its 200 kept for renewals). Every 25 seconds the stream checks its renewal: sent 30 to 55 seconds after the renewal opens (half the deadline), again 60 to 85 seconds later while unanswered. The stream ends gracefully (the `subscriptions/listen` result) when its socket closes (expired, revoked, slow, resynchronized), before its controls run out, and after 2 hours (to the next 25-second check): listen again, then read again. Closing the stream closes the socket; a response the client never read renews nothing, so its socket closes at its deadline (10 minutes). Keepalive comments every 25 seconds while nothing else is sent |
| First request on a new isolate | **Measured** on Workers Free (2026-10-14): 60 to 190 ms of CPU for `tools/list`, paid once per isolate: loading the Worker's code, the MCP SDK building its protocol schemas on first use, and converting every tool's schema. New isolates are most common right after a deploy and when traffic grows |

On Free, whose nominal CPU limit is 10 ms per request
([platform limit](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)),
those first requests completed in the measurement, but they run well past the
nominal limit, so a burst of new MCP clients just after a deploy is the
likeliest place for a Free deployment to hit it (the request then fails with
error 1102). Paid's default is 30 s. Not measured yet: the same on Paid,
and how often Free actually enforces the limit for these requests.

## Templates

`POST /repos/{template_owner}/{template_repo}/generate` makes a repository
whose first commit holds the template's default-branch tree. The template's
object reads the tree; the new repository's object commits it through the
push path, as a file write.

| What | Value |
|---|---|
| Trees and files copied | 2,000 at most |
| Their bytes | 8 MiB at most (they cross between two objects and are packed); larger answers 422 `template_too_large` |
| Storage reads | The browse budget (800 R2 reads); more answers 422 `too_expensive` |
| History | None: one commit on `main`, `Initial commit`, by the caller |
| Token | Needs `contents:write` too, without a repository list |
| A failure | The new repository's object settles it: if its first commit was made (the answer was lost), the repository is kept; otherwise its commit is refused from then on and the repository is deleted, its name free once the deletion finishes |
| A request that never finished | The cron settles the generation the same way once it is 15 minutes overdue; while the generation is pending, the repository takes no write |

## Stars

A star is one directory row per user and repository. Starring needs
`starring:write` and `metadata:read` on the repository; `GET /user/starred`
needs `starring:read`. A repository's `stargazers_count` counts stars of
enabled users. Deleting a repository deletes its stars. A listing leaves out
repositories the caller can no longer read, so a page can be short.

## Commit signing

Commits Fyrden makes itself (file writes, generated repositories) are signed
with the platform's Ed25519 key as SSH signatures (`gpg.format = ssh`), so
`git verify-commit` checks them against the published key. Every commit in
the API carries GitHub's `verification` object.

| What | Value |
|---|---|
| The key | The Worker secret `SIGNING_KEY`: a 32-byte Ed25519 seed, base64. `fyrden deploy` makes one when the Worker has none and never shows it |
| Published at | `GET /api/meta/signing-keys` (any token; the `list_signing_keys` MCP tool): each key's `key_id` (the SHA-256 fingerprint ssh-keygen shows), its public key line, and whether it is current |
| Rotation | Set a new `SIGNING_KEY` and list the old public key line in `SIGNING_KEYS_RETIRED` (one per line), so commits it signed still verify |
| Verified | A valid signature by the platform's key, current or retired; or by a key a user (or an agent, with its own token) added (`POST /user/ssh_signing_keys`) on a commit whose committer email is that principal's no-reply address, `<user or agent id>@users.noreply.<host>` (else `bad_email`) |
| Users' and agents' signing keys | Ed25519 only; 100 per user or agent (an agent adds its own with its own token); a key belongs to one of them (`key_in_use`); deleting one unverifies what it signed, and so does disabling its user, its agent or the agent's owner |
| Not verified | `unsigned`, `unknown_key` (valid, by a key Fyrden does not know), `invalid` (the commit or signature was changed), `malformed_signature`, `unknown_signature_type` (OpenPGP, or a key type other than Ed25519) |
| Without `SIGNING_KEY` | Fyrden's commits are unsigned |
| A malformed `SIGNING_KEY` | Writes it would sign are refused (logged); reading and verifying go on, with the keys that can be read |
| Signatures read | 64 KiB at most; a longer `gpgsig` is `malformed_signature`, not shown |

## Rulesets

Repository rulesets (`/repos/{owner}/{repo}/rulesets`, GitHub's shape) hold
rules on the branches or tags whose full names match: `creation`, `update`,
`deletion`, `non_fast_forward`, `required_signatures`, `pull_request` (no
direct change at all; changes come through pull requests), and Fyrden's
`require_up_to_date` (a pull request merged into the branch must already
contain its latest commit; GitHub ties this to required status checks, which
Fyrden does not have yet). Bypass is by repository role; Fyrden's
`actor_types` limits a ruleset to principal types (`["agent"]` with
`pull_request`: agents must use pull requests).

| What | Value |
|---|---|
| Rulesets per repository | 50 |
| Checked before anything is stored | `creation`, `update`, `deletion`, `pull_request`: a push whose every command is refused is answered before its body reaches R2 (repositories with such a ruleset read the push's command section first, up to 1 MiB; of a gzip body, its first 64 KiB, inflated to at most 1 MiB; a command section past either bound is checked at the commit only; others stream it to R2 untouched); an upload session or a file write a rule refuses answers 409 `ruleset_violation`; an import a rule refuses fails after listing the source's refs, before fetching |
| Checked at the commit | Every rule, with the rulesets current then (a change of the rulesets, the default branch or the pusher's role in between refuses the push; push again): force pushes against the commit graph, signatures of every new commit (reachable from the new tip, not from that ref's old one; ancestors from other branches included) |
| Required signatures | Branch rulesets only. Each new commit verified as the API shows it (platform key, or a user's key on that user's commits); at most 1,000 new commits per ref update (and 20,000 commits walked to find them), more is refused (push in parts); commits are read from the repository's packs and the push's own, once a push however many refs share them, within 800 R2 reads for the whole push (a commit not read by then is refused as `unreadable`) |
| Default branch | `~DEFAULT_BRANCH` names the current default branch and, for an import, the one it sets |
| Refusal text | 2,000 bytes at most per ref |
| Refusals | `ng <ref> <reason> (ruleset "<name>")`; an atomic push fails as a whole |
| `evaluate` | Does not block; what it would have refused at a push's commit point (its signatures too) is listed at `GET /repos/{owner}/{repo}/rulesets/rule-suites` (MCP `list_rule_suites`): one suite per ref update one of them objected to, the newest 1,000 kept, nothing for an update they all let through |
| Actor types | Each principal type at most once |
| `pull_request` parameters | GitHub's: `required_approving_review_count` 0-10, `dismiss_stale_reviews_on_push`, `require_last_push_approval`, `required_review_thread_resolution`, `allowed_merge_methods` (`merge`, `squash`, `rebase`; each once); `require_code_owner_review` (see Code owners' review), `required_reviewers` empty (required team reviews come later); any other parameter is refused, never stored unenforced. Fyrden's `allow_agent_approvals` (default false): reviews submitted by agents count, a person's own agents as that person. A rule stored without parameters reads as all defaults (no requirement beyond the pull request) |
| Approvals | One vote per person (an agent acting for a person, or a person's own agent, is that person); the author's never counts; only people with write access or above count, checked when merging; a person's latest review that is not a comment and not dismissed stands; an eligible request for changes blocks until that person approves or it is dismissed |

## Pull requests

Pull requests between branches of one repository
(`/repos/{owner}/{repo}/pulls`, GitHub's shape; MCP `create_pull_request`,
`list_pull_requests`, `get_pull_request`, `update_pull_request`,
`merge_pull_request`). The head may be a branch of a fork in the same network (`owner:branch`).

| What | Value |
|---|---|
| Title | 1-256 characters |
| Body | 65,536 characters at most |
| Numbers | Per repository, from 1, in order; shared with issues once they exist |
| Heads in forks | `head` is `owner:branch`: a branch of that owner's repository in the base's fork network, which the caller must be able to read. With `head_repo` the repository is named exactly, whatever else the owner has. Without it, the owner's first 10 active repositories in the network by name are looked at and only those the caller reads count: one is taken, two or more answer 422 `head_repo_required`, none 422 `head_not_found`. A repository the caller cannot read is never named or counted in an answer, but it takes one of those 10 places, so two inferences remain: a caller answered `head_not_found` for a repository it reads learns that at least 10 of the owner's repositories sort before it, and a second readable repository past the first 10 goes unnoticed (the one readable among them is taken). Name the repository with `head_repo` to avoid both. Its revision is imported before the pull request opens (no pack byte copied: the fork's packs are borrowed, recorded by the network; its commits the base lacks are copied, 50,000 at most, else 422 `too_expensive`; 422 `view_full` when the base cannot borrow more packs, see Borrowed packs). Each later push to that branch is told to the base and imported in the background, in order (a late notice of an earlier revision is ignored); a deleted branch shows `head_ref_deleted`, the pull request staying at its last revision. Closed or merged, the branch is no longer followed; reopened, it is again. A fork restored from a backup that predates a pull request's following asks every other repository of its network, in the background once it takes its new restore generation, to follow its branches again; the pull request then takes the branch as it is. Only the pull request's revisions become readable through the base (`refs/pull/<number>/head`): nothing else of the fork is served. The pull request's author must still read the fork for revisions to be imported |
| Writing a head branch in a fork | Updating the branch, resolving conflicts and applying suggestions build the commit in the base and hand it to the fork, which commits it through its own push path (its rulesets apply; the branch moves only from the head the base last imported, else 409 `head_moved`). The caller needs write access to the base, and write access to the fork or the pull request's `maintainer_can_modify`: set by its author only (when opening it or later), meaningful only for a head in a fork (always `false` otherwise), and honored only while the author still writes the fork and is not disabled (an agent author: nor its owner) (403 `maintainer_edits_off` otherwise). | Opening | Anyone who reads the repository (`pull_requests:write`). | Head branch deleted | The pull request keeps its last head (`head_ref_deleted: true`) and stays open; it cannot be reopened until the branch exists again, and follows the branch again once it does |
| Changes | The author (anyone acting as the same person, such as its agents within their own roles) edits, retargets, drafts, closes and reopens its own pull request with any role that reads; on someone else's, triage closes and reopens, write does the rest. | Reopening | Needs the head branch and the base branch (unless the same patch retargets onto an existing one); moves `refs/pull/<number>/head` to the head branch's tip |

| Reviews | Anyone who reads the repository may approve, request changes or comment on an open pull request (MCP `submit_review`); the author may only comment. Whether a review counts toward a merge is decided when merging (see Rulesets) |
| Dismissing a review | Write access, with a reason of 1-1,024 characters; only a standing approval or request for changes; the review is kept, shown as `DISMISSED` with who and why |

| Activity feeds | Threads `issue/{number}`: the mentioned hear of an issue's opening and of new mentions in its body and comments; its participants (author, commenters, the mentioned, assignees) of its comments, closing and reopening. Feed items show only to a token that reads their kind |

## Labels, milestones and assignees

Issues and pull requests alike: GitHub's paths, through the issue endpoints for a pull request's number too. Reading labels and milestones takes `issues:read` or `pull_requests:read`; managing them takes write access and `issues:write` or `pull_requests:write`; changing what an issue or pull request carries takes triage and the write permission of its kind (a token without it gets 404 for that number). A locked conversation does not stop any of them.

Measured on Free: making 20 events' deliveries in one invocation took 42 to 86 ms of CPU (2026-10-17, `wrangler tail`), about 2 to 4 ms an event, and events consumer invocations of 136 ms were not stopped (2026-10-21); a message names 2 so that messages run side by side. Messages are taken side by side (Queues runs up to 250 consumer invocations at once, scaling with the backlog: [platform limit](https://developers.cloudflare.com/queues/platform/limits/)). Those an invocation made but had not marked done are made again with the same ids, as after any lost acknowledgement. An effect whose source repository was deleted, restored to an earlier state or transferred since it was journaled is ended without its deliveries (`effects.invalidated`). Failures to send, claim or deliver are logged and counted (`effects.dispatch`, `effects.consume`, `effects.recover`; see metrics.md); `GET /healthz` reports `checks.effects` as not ok, without failing the health check, once the oldest pending effect is 15 minutes overdue, or while an effect failed for good (not ended because its source went) in the last hour (both Proposed), with only that age (`overdueS`) and that flag (`failed`). On Workers Free each queue message costs about 3 of the 10,000 queue operations a day ([pricing](https://developers.cloudflare.com/queues/platform/pricing/)): an event with webhooks costs its events message, a share of a webhook effects message, and one message per retry and per first attempt past its first 2 deliveries (an estimate: the deployed figures are in the Free run's record). What happens to sends once the day's operations are spent is not documented by Cloudflare; whatever it is, a refused send leaves the effect journaled and overdue, the effects cron sends it again every 5 minutes, and `checks.effects` reports it late, so deliveries resume, late, once sends are accepted again (a refused send spends no attempt; a delayed message is sent at most 12 hours ahead, within Free's 24-hour message retention: [platform limit](https://developers.cloudflare.com/queues/platform/limits/)) |
| Repairing effects | An effect that failed for good (its attempts spent, for instance while a feed or a repository object could not answer for hours) stays failed: nothing retries it. While what it delivers can still matter (within 7 days of its change, Proposed: feeds drop older entries on arrival), an operator reopens it with `fyrden effects repair --url <API URL> --sink feed\|webhooks\|references --since <date>` (an instance administrator's token in `FYRDEN_TOKEN`; it calls `POST /api/admin/effects/repair`, Fyrden's), which counts them, and with `--yes` reopens up to 1,000 a run (the oldest first; run again for more) through the read model's executor, refused (503 `read_model_maintenance`) while the read model is under maintenance, keeping their ids and what they carry (their attempts count again from one, so one ever claimed still counts as claimed when its repository is deleted); the effects cron sends them with the other overdue effects, 100 a run every 5 minutes, the longest overdue first (1,000 take at least 50 minutes, so a page near its deadline may still expire), and their claims check their sources again, so one whose repository was deleted or restored since is ended, not delivered, as is a feed or webhook effect whose repository was transferred (references stand across transfers). Past 7 days nothing is repairable; the effect stays failed, and its recipients' feeds go without it |

Proposed capacity: each run of the effects cron (every 5 minutes) deletes up to 1,000 expired deliveries with their attempts, each event's together (they share its body, deleted with the last of them), in three D1 queries and one bulk R2 delete of their bodies (a dropped delivery's body was never stored and costs none): 288,000 a day. ## Activity feed

Each user and agent has an activity feed of the pull requests that need it
or that it takes part in: `GET /feed`, `GET /feed/sync` and
`POST /feed/ack` (MCP tools `get_feed`, `sync_feed`, `ack_feed_item`), for
any user or agent token or a signed-in session, without a permission of
their own.

| What | Value |
|---|---|
| Whose feed | The token's principal's: an agent's own token reads the agent's feed; a delegated token, whichever agent of its chain holds it, reads the user's; a session reads its user's. Acknowledgements are the feed's, shared by everyone who reads it |
| Read-time checks | Every list, sync and acknowledgement checks each repository of its items again: the repository must exist and the caller must have `pull_requests:read` there now, within its token's scopes and repositories (a delegated token's grant) and its agents' owners' rights, in one call to the repository's object, which also gives what the page's members say, and, for a repository that call lets the caller read, confirmed by the repository's account's object (one call an account on the page: the caller's role and its agents' owners' roles as the account has them now, so a lost notice to the repository of a role taken away hides its items at once; a repository the account gave away by a transfer reads through it for no one). Both must allow an item, judged under the same account: an answer for another (a transfer between the two calls, or between the check and a later read of members) is a check not made. A fresh denial hides items and forgets nothing. Before reading the feed at all, every list and sync verifies the caller's credential again on the directory's primary (a revoked token, or one whose owner now requires DPoP, is refused 401 at once, whatever the feed holds). Items it fails are left out without saying how many: a cursor records only what the caller was shown (see Order and cursors), so an answer, its cursors and its ETag change only when what the caller may see does. One answer checks at most 100 repositories and reads at most 1,000 items (Proposed); past that, or when a check cannot be made, it ends at the last item shown and never moves past an item not checked. When a check finds for certain that the feed's owner itself cannot read a repository (it is gone from the directory or its object, or its owner is disabled; or the owner's own access, with its agents' owners' rights for an agent, says so by the account's ACL snapshot the repository decided with, pulled at most 60 seconds before), the feed forgets that repository's items as losing access does (see Lost access), whichever token read it: up to when that snapshot was pulled (or the repository was found gone), as a notice of that ACL version would, so never past a newer version's notice, and activity of access given back since that time stays. A token's own limits (scopes, repositories) or a delegated token's grant forget nothing, and a check that cannot be sure (the repository has no usable snapshot, as when the account's object fails to answer, or a transfer is moving it, its collaborators let go by the old account before the new one takes them) counts as a check not made: it ends the answer there and forgets nothing. So however many such items come first, a later answer gets past them (one more answer per 100 such repositories or 1,000 such items), and a cursor never names one. Such an answer looks like one that found nothing new: `poll_after_ms` is 0 only after a full page. What a caller can still tell: items it may see can come an answer or more later than without the others (see Cursors and hidden items). A sync whose checks run out on such repositories answers `complete: false` once, its cursor then reading every stream from what the feed keeps of it, while their items are forgotten; the next sync answers `complete: true` with the same items and a cursor following on in the streams it gave items of. A known limit: a delegated token whose acting agents' owners cannot read more than a budget of repositories its user reads (so nothing is forgotten) stays behind their items until retention or their streams' caps remove them. An acknowledgement of an item the caller may not see is 404 |
| Items | One per repository, thread and kind (`review_requested`, `changes_requested`, `approved`, `merge_conflict`, `mention`, `activity`), updated in place. A change applies only from a newer version of the thread (ordered by the repository's restore generation, then the thread's version: a restored repository's versions start again, and are newer than any from before; a delivery from before the restore arriving late changes nothing; an `activity` item keeps only the newest generation's members), so duplicate and reordered deliveries leave the same item. An entry that only resolves an item the feed has not shown shows nothing: it is kept as an unseen tombstone (not listed, synced or counted in the cap), so an older entry that opens the item later shows it with the newer state rather than reopening it. An `activity` item gathers the ids of its comments and reviews: the greatest 100, `members_truncated` once any was dropped. An `activity` item displays its greatest member (ordered by id, longer ids greater) and that member's author and the author's access, whatever order its comments arrive in. Items hold ids, not text: the excerpt is read from the repository when the item is read, with the same call that checks access (at most 100 members a call), so an edit shows at once and a deleted comment shows none. A change made by the owner itself (`silent`) still updates its item, reopening it included, without a notification |
| Mentions | `@handle` of an active user or agent who reads the repository, in a pull request's description, a comment, a review or a review comment (an edit tells only the handles it adds); 50 a text at most. Read as the page shows the text (GitHub-flavored Markdown): not in code, link targets, images or footnotes. Only a text's first 16,384 characters are read: a longer one up to its last blank line before them, so no handle or reference is cut short and no code is opened (a longer one with no blank line there is not read), and a text that would be costly to parse (more than 256 emphasis delimiters, 256 opening brackets, or 128 quote and list markers) mentions no one |
| Order and cursors | A feed is made of streams: a repository's issue threads, or its pull requests'. Every change of an item, an acknowledgement included, takes the feed's next sequence number, and the feed reads in that order, so following `next_cursor` never skips a change, however late it arrives or whenever it lands while an answer reads; a changed item comes again. Its retention clock is when it changed, never before its stream's last change (so a clock gone back cannot expire a stream's later items before its earlier ones, and no other stream moves it). A cursor names a snapshot the feed keeps for the credential that got it (`base64url` of a version, the feed's epoch, the snapshot's random id, and the count of quiet answers, see Polling): in each stream it was given items of, the sequence number of the last one, at most 1,000 streams (Proposed). Only what an answer gives moves a stream's position; nothing the caller may not read moves, expires or evicts anything of its cursor. A cursor is the credential's own (another token or session of the same principal gets 410) and lasts a day from its snapshot's making (Proposed); reading on renews it (an answer whose snapshot is past half that keeps a new one), and a credential keeps its latest 50 (Proposed). An answer that gives nothing names the same snapshot and writes nothing until the renewal. A stream deleted from (retention, its cap) while an answer reads it, past where the answer had read, makes the answer 410 rather than pass what it had not read. Past 1,000 streams with positions, the cursor reads those streams only, and items of others are left out until a sync starts a new one: answers say `coverage: "partial"`. A quiet poll reads about 6 rows a stream with a position; on a feed with more than 1,000 streams holding items, an answer reads from what the feed keeps (its rows already given included), and a cursor of before streams is expired. The epoch includes the restore generation the directory keeps for the feed (`source_epochs`, key `feed:<principal id>`): a restore of the feed's object allocates the next one there, as for a repository's, so cursors made before it expire. A feed object reads the directory once an instance, before its first call or alarm does anything (that generation, and whether its principal is being deleted, whose feed it then retires): a cold feed's first delivery makes one more D1 query, and while the directory cannot be read, deliveries to cold feeds fail and are retried as any failed delivery is, and a retention alarm waits a minute (Proposed) and tries again. Cursors of before streams (one sequence number of the whole feed) are still read, as every stream at that number, judged by the feed's head and low watermark when it migrated, and answered with a snapshot's; they stop being read in a later release. While a deploy replaces Workers of the earlier version, their feed reads fail (500) rather than make cursors of the earlier kind. A feed migrated to streams (one pass at its object's first wake, linear in its rows: a feed of 5,400 items, 20,000 tombstones and 1,000 fences read about 22 rows and wrote 6 a row, about 0.2 seconds locally, 2026-10-27; on Workers Free, a feed past about 16,000 rows would take more than a day's writes, and fails to wake until the next day's) keeps every item's number and acknowledgement. `poll_after_ms`: 0 after a full page, else see Polling |
| Polling | `poll_after_ms` is 30 seconds after an answer that showed something, or a sync, and doubles with each answer in a row that showed nothing, up to 30 minutes (both Proposed): 60 seconds, 2, 4, 8 and 16 minutes, then 30. The count travels in the cursor (`q`, at most 6), so nothing is stored per poll, and at the ceiling a quiet feed's answer, cursor and ETag stay the same (304 with `If-None-Match`) until the cursor's snapshot is 12 hours old, when the answer names a renewed one (one more request, and about 7 rows written over the snapshot's life: kept, scheduled and deleted when it expires; twice a day an idle client). It counts only what the caller sees: an answer that showed nothing is quiet whatever it did not show, one that stopped short on items the caller may not see included. Each poll is a request to the feed's Durable Object; a quiet poll is only that one (no repository is checked), reading about 6 rows a stream with a position (counted locally, 2026-10-27), and an answer that gives something is one more, to keep its snapshot. Workers Free allows 100,000 Durable Object requests a day, each RPC call to a stub one (verified, <https://developers.cloudflare.com/durable-objects/platform/pricing/>, 2026-10-16). At a fixed 30 seconds a client makes 2,880 polls a day, so 35 clients polling all day would exceed it. With the backoff (arithmetic, not measured) an idle client makes 6 polls in the 31.5 minutes after the last answer that showed something, then at most 48 a day, and renews its cursor twice a day (2 more requests and about 14 rows written): about 55, so 1,000 idle clients make about 55,000 requests and write about 14,000 rows a day, roughly half of Free's requests, before deliveries, acknowledgements, repository checks and alarms; feed reads alone would take all of it at about 2,000 idle clients. A feed that changes between every poll keeps its client at 30 seconds: the cost follows activity. A client may poll later than `poll_after_ms`, never sooner |

## Watching

A principal sets its level for a repository it reads: participating (the default: told of the conversations it takes part in), watching (told of every conversation's activity and of new ones, `P2` in its feed), or ignoring (kept and reported; it suppresses notifying, which comes with the inbox): `GET/PUT/DELETE /repos/{owner}/{repo}/subscription` and `GET /user/subscriptions`, as GitHub's (MCP tools `watch_repository`, `unwatch_repository`), with `watching:read` or `watching:write` and `metadata:read` on the repository. And for one issue or pull request it may read, its own preference: subscribed (told of its activity as a participant is, P1) or unsubscribed (kept and reported; it suppresses notifying, which comes with the inbox): `GET/PUT/DELETE /repos/{owner}/{repo}/issues/{issue_number}/subscription`, a Fyrden extension at Gitea's route (GitHub's thread subscriptions come with notification threads; MCP tools `subscribe_to_thread`, `clear_thread_subscription`), with `watching:read` or `watching:write` and `issues:read` or `pull_requests:read` by the conversation's kind (any other kind, or none, answers 404 `issue_not_found`).

It is turned on in a deployment after a release whose every Worker and object reads P2 entries, and events carrying their watchers apart (the release that admits them against the daily allowance), has fully rolled out; once on, a rollback goes to an off deployment of such a release or forward, never below it (queued events and stored P2 entries remain). ## Discretionary work

Watched activity (P2 entries) is the work a deployment may leave out: on Workers Free the account's daily quotas (Durable Object rows written and requests, D1 rows written, queue operations; reset at 00:00 UTC) are shared by everything, and once one is spent every core write fails until midnight. So watched entries are admitted against a daily allowance, and everything else (things to act on, threads one takes part in or subscribes to, cleanup) never consults it and is never refused.

| What | Value |
|---|---|
| Admission | An event's watchers' entries are one effect, admitted when the events consumer journals it (in the same D1 batch, no extra call): journaled only when the day's admissions, from the hour before the day's start (by the database's clock) to now and any later hour, plus its price, stay within the allowance in every resource, and the day has refused nothing yet (so admissions follow arrival order). A refused one is never journaled or delivered (`effects.refused`); the day's first refusal is recorded once, and nothing more is written for later ones. An event delivered again admits nothing again |
| Price | Its whole life at its worst (Proposed, measured locally 2026-10-27): per watcher, one Durable Object request, 300 rows read and 45 written (a new item at its stream's cap and a new inbox thread at its inbox stream's cap, each with its eviction and fence: 237 read, 27 written; a feed's first entry: 18 read, 15 written, and the schema of a feed made for it; the epoch's adoption, the alarm, and the item's and thread's later deletion), half a second of the object's time, and eight directory rows read (its cold epoch read, 2, and its preference read, 3 to 5, measured locally); per effect, 100 D1 rows read and 24 written (its journal row's life at its worst: inserted, sent, sent again, claimed and given back, ended and pruned, with their indexes, measured at 53 read and 20 written; and its admission, which reads up to 26 hours' rows) and 6 queue operations (a message and one sent again by the effects cron, inline or not) |
| Allowance | `FYRDEN_DISCRETIONARY_DAILY` (`resource=n,…`: `do_requests`, `do_rows_read`, `do_rows_written`, `do_duration_ms`, `d1_rows_read`, `d1_rows_written`, `queue_ops`; `fyrden deploy --discretionary` sets it). Free: each resource as set, at most Free's daily limit, else a fifth of it (Proposed: 20,000 requests, 1,000,000 rows read, 20,000 rows written, 20,312.5 s of duration (Free's 13,000 GB-s at 0.128 GB), 1,000,000 D1 rows read, 20,000 D1 rows written, 2,000 queue operations); queue operations bind first, at about 330 events with watchers a day. Paid: only the resources set are capped (scale is billed, not refused); with none set, nothing is admitted or recorded. A value not readable whole is ignored (the plan's default) |
| Delivery | Once, within an hour of admission: a failed or lost attempt is not retried (the effect fails: `attempts spent`, or its error; a feed whose preferences could not be read fails its call likewise), one claimed but given back unstarted is not claimed again, and an entry reaching its feed after the hour (a call started late, a cold object's directory read held) is dropped there and its effect ends `expired: past its admission window`, while the same call's other entries apply. `fyrden effects repair` never reopens them |

Estimated, not enforced (measured on Free before watching is switched on): an object's active time (a pending call has no platform limit; priced at half a second a call); the later deletion of what watched entries made (priced at admission, done when retention, a purge or retirement reaches it: later, and later still after an outage); a feed object's one-time migration when a watched entry is the first to wake it; queue traffic past one send and one recovery |

## Email

A user's notification addresses, managed from Fyrden's web pages signed in: `GET`, `POST` and `DELETE /user/emails` (GitHub's shapes) and `POST /user/emails/confirm` and `/user/emails/confirmation` (Fyrden's). Email is sent only while the deployment's sending is on (`fyrden deploy --email resend … --email-sending on`); while it is off, adding an address or asking for a confirmation answers 503 `email_unavailable`, and no notification email is queued. Notification email also needs the deployment's public origin (`FYRDEN_PUBLIC_ORIGIN`). People manage their addresses (add, confirm, ask for a new link, remove) and which notification email they get on the web page `/settings/notifications`, which every notification email links to.

| What | Value |
|---|---|
| Who | Web sessions only (`emails:read`, `emails:write`: no token, OAuth client, agent or delegation carries them, and any other credential gets 403). An unrestricted personal access token is the user's full authority and can start a session, so its holder can manage addresses through one, as it can add a passkey |
| Addresses | At most 10 live a user (422 `too_many_emails`); one at most 254 bytes, one `@`, a domain with a dot, nothing more checked; the same address in another case is the same mailbox. An address added again after its removal is a new one (its id is its generation): nothing of the earlier one applies to it |
| Confirming | Each address added is mailed a link (32 random bytes, kept as their SHA-256) to the web page `/settings/emails/confirm`, which confirms only on its form's post from Fyrden's own origin, by the signed-in account that added the address, once, within a day. A link of another account, used, expired, replaced by a newer one, or of an address removed answers 404, the same for all, and is not used up. A mailbox is verified on one account at a time: confirming one another account holds verified answers 409 `email_taken` (the link used up), and a verification, or the removal of a verified address, makes every outstanding link of that mailbox stale |
| Limits | Confirmation emails: 5 a user an hour, 3 a mailbox a day whoever asks; a request needing more is refused whole (429 `confirmation_rate_limited` with `Retry-After`, nothing added or counted) |
| Sending | Right before each provider call one directory batch checks that the user still holds at the generation it signed in at, the address is still theirs and unverified, its link the current one, the mailbox not suppressed, and the allowance has room, and reserves the message only when all hold; a change after it cannot recall the call. An address is added whether or not its confirmation could be sent: asking for one again (`POST /user/emails/confirmation`) says why it was not (503 `email_unavailable` with `Retry-After` when the allowance or the provider's rate limit is spent, 422 `email_undeliverable` when the mailbox is suppressed; an unknown outcome answers 204, as it may have been sent). Nothing is tried again by itself |
| Allowance | The provider's messages a UTC day and a UTC month: `FYRDEN_EMAIL_DAILY_LIMIT` (default 100) and `FYRDEN_EMAIL_MONTHLY_LIMIT` (default 3,000: Resend Free's), set with `--email-daily-limit` and `--email-monthly-limit`. Each call reserves one message in both or neither; a refusal gives it back, an unknown outcome keeps it. Notification email will stop `FYRDEN_EMAIL_RESERVE` (default 10, `--email-reserve`) short of both, so confirmations keep room. A daily limit of 0 turns email off; otherwise `0 ≤ reserve < daily ≤ monthly`, or email is off (logged). Rows are kept for the current and the last period. Calls in flight across midnight count in the day they were reserved in. The provider's own quota also counts mail sent from its account outside Fyrden |
| Suppression | Fyrden keeps a copy of the provider's suppression list (a mailbox that bounced, whose owner marked the mail as spam, or the operator suppressed): sent nothing, refused when added (422 `email_undeliverable`, nothing added) and listed with `deliverable: false`. Kept by the provider's callbacks `suppression.added` and `suppression.removed` to `POST /auth/email/events` on the public origin (Standard Webhooks signatures with the Worker secret `RESEND_WEBHOOK_SECRET`, five minutes' tolerance; 64 KiB bodies; requests that do not verify: no directory work, 120 a minute a client address). Ordered by each suppression's creation time and id, so redeliveries, replays and any order of arrival end where the provider is. A suppression whose removal never arrived is rechecked with the provider 7 days after it was last confirmed, at once when an add or a resend meets it: up to `FYRDEN_EMAIL_RECHECKS` (default 3, at most 10) a maintenance run, in a request of their own, one at a time; a provider failure moves that row an hour on and ends the run's rechecks. Rows are a mailbox's (one a mailbox ever suppressed, its lower-cased address), never reaped, and not removed with a user |
| Primary | `primary` is the address notifications will go to: the earliest verified. GitHub's other deviations: no pagination, `visibility` always null |
| Cleanup | Links go a day after their expiry or use, counters after their period, addresses 30 days after their removal, a mailbox a day after no live address names it: by indexes, 1,000 rows of each a maintenance run. A user's deletion removes their addresses with its other rows |
| Settings | `GET` and `PUT /user/notification-settings` (Fyrden's; web sessions only): which notification email is sent, by category: `direct` (a review requested of you or your team, an assignment, a mention, your own issue or pull request closed, reopened, merged or in conflict; on unless set), `participating` (activity on threads you take part in or subscribed to; off unless set), `watching` (activity in repositories you watch; off unless set; saved, but not sent yet: its sending work is not priced as other watched work is). An event's email takes the strongest category its entries for you reach, decided by that event, never by a thread's earlier reasons; what only settles something, and your own actions, are never emailed. A `PUT` sets the fields given, the last write winning. Digests are not emailed |
| Notification email | One message an event for a recipient. The repository decides which email an event makes for each recipient from all its contributions (`direct` or `participating`, and the reason: a mention, a review request, an assignment, an author's state change, a comment) and marks one of its entries; the recipient's feed queues it when the recipient has a verified address the provider does not suppress and the category on (at most 200 queued: past it, expired ones go first, then the newest of the lowest category, the incoming one included). Its object's alarm sends up to `FYRDEN_EMAIL_SENDS_PER_ALARM` (default 3, at most 5) a run, oldest first, each read as the recipient reads it then (its repository and thread readable, the thread's number still naming its conversation; the comment's text read fresh, none once deleted; its title as it is now) and admitted by one directory batch: the event under 24 hours old, the user active, the repository not ignored, the conversation not unsubscribed (unless it asks something of the recipient: a mention, a review request, an assignment), the category on, an address (the earliest verified one not suppressed), no unsubscribe of it from the category, no outcome yet for that event, and room in the allowance short of the reserve. Plain text: who did what, the comment's text, the thread's link on the public origin, why, and one-click unsubscribe (`List-Unsubscribe`, `List-Unsubscribe-Post`) and settings links (`/settings/notifications`) |
| Once | Each email's outcome is kept in the directory by recipient and event (`sending`, `sent`, `unknown`, `refused`, `retry`, `exhausted`), written before the provider call: an email goes at most once, whichever copy of the recipient's object holds it, a restored one included (a candidate a restore brings back that was never sent may still be, if it is eligible then). A transient refusal gives the message back and is tried again after a back-off (5 minutes, doubling, never before the provider's delay), at most 4 attempts, each with its own idempotency key; an unknown outcome, or a crash after the directory's batch, is never tried again. Kept 30 days after the event (by an index, 1,000 rows a maintenance run) and removed with the user |
| Attempts | Send attempts a UTC day, whatever their outcome: `FYRDEN_EMAIL_ATTEMPTS_DAILY` (default twice the daily limit), taken before a candidate is read, never given back; spent, candidates wait for the next day (within their 24 hours). This, not the provider allowance, bounds a day's sending work |
| Unsubscribing | Every notification email carries a one-click link (RFC 8058: `List-Unsubscribe` and `List-Unsubscribe-Post`, and in its footer) to `/unsubscribe` on the public origin, signed with the Worker secret `EMAIL_KEY` (its own: rotating the commit signing key leaves links working; replacing it, only after a compromise, breaks every link sent). A link names one address (as added: added again, it starts clean) and one category. A `POST` with no credential and any body unsubscribes it (answered 200 whether or not the address still exists, writing nothing then); `GET` and `HEAD` show a page that changes nothing, with a form posting the same. One-click posts: 10 a minute an address and category; links that do not verify: 120 a minute a client address (429 with `Retry-After`). Unsubscribes go with their address |
| Provider | Resend (`FYRDEN_EMAIL_PROVIDER=resend`): a message is accepted only when Resend answers with its id; refused when it answers that the request is at fault (never sent again) or limited for now; any other outcome (a server error, no answer, an answer without an id) is unknown and never sent again. Each message carries an idempotency key, and tags naming its kind and address for the provider's logs |
| Turning sending on | `fyrden deploy --email resend --email-from ADDRESS --email-secrets-file PATH --email-sending on`, the file holding `RESEND_API_KEY` (a full-access key: the deploy refuses one that cannot read the suppression list) and `RESEND_WEBHOOK_SECRET`. Make the webhook first: `resend webhooks create --endpoint https://<web origin>/auth/email/events --events suppression.added suppression.removed`, its signing secret into the file. Without the secret, a key or usable limits, nothing is sent. Passed on every deploy, as the provider is |

## Live hints (off unless turned on)

A WebSocket that hints which of the caller's feed and inbox streams changed, so a page or client rereads them through the REST APIs. MCP clients get the same hints for their feed over `subscriptions/listen` (see MCP server), each stream one of these sockets. Off until the deployment turns it on (`fyrden deploy --live on`), after its workload is measured on the deployment's plan; while off, `POST /notifications/live` answers 503 `live_unavailable`.

| What | Value |
|---|---|
| Opening | `POST /notifications/live` (the caller's own credentials: a session, or a token of the principal itself; a delegated token gets 403 `delegated_listing`) answers a single-use ticket good for 30 seconds and the URL to open. The upgrade (`GET /api/notifications/live?ticket=`) needs the same credential: the session's cookie with the request's `Origin` this deployment's own, or the token in `Authorization`; another credential's, a used or an expired ticket: 401, the ticket unspent when the credential does not match |
| Admission | Each socket holds a lease in the directory (`live_sockets`, with the dependencies its credential rests on): at most `FYRDEN_LIVE_SOCKETS` (default 50) at once in the deployment (503 with `Retry-After` past it), 60 opened a principal a day (429), 5 a credential and 20 a principal at once (429); confirmed by the feed's object before anything is sent, released at close; leases whose release was lost are reaped by the maintenance run (1,000 a run) |
| Frames | `{"t":"changed","n":<counter>,"streams":[{"repo":<id>,"kind":"issue"|"pull"}]}` (more than 20: `"refresh":true`): only streams of repositories the credential may read now (its token's repositories and scopes, then the repository's own decision, made afresh by every run that sends, with the credential checked again), with a change its current preferences let through (an ignored repository's never; an unsubscribed conversation's only what asks something of the principal; the principal's own read, done and acknowledgement always, for its other tabs). What it cannot read never enters its frames, window or closes; when frames go and how many changes one coalesces may depend on other work in the object. A stream whose repository's access cannot be decided is passed over: clients reread on every renewal and reconnect |
| Flow control | The client acknowledges frames (`{"t":"ack","n":…}`): at most 8 unacknowledged; past them changes wait and coalesce; full for 2 minutes, the socket closes (4409: reread everything). Control messages: at most 1 KiB, 20 a minute, 200 a socket's life (past any: 1008) |
| Renewal | Every 10 minutes (`{"t":"renew"}`, answered `{"t":"renewed","until":…}`; earlier than half the deadline does nothing): the credential checked again on the directory's primary; no longer holding, or unanswered twice: closed (4401). A socket lives at most 24 hours (or its credential's expiry); then a new ticket |
| Revocation | Revoking a token or session, a grant, or suspending, deleting or disabling a principal writes a row (`revocations`) in the revoking statement's own transaction (the directory's triggers). The maintenance run finds the sockets resting on it through the dependency index (1,000 index rows, 50 revocations a run, from a kept cursor) and tells their feeds (200 a run, 8 at once; a failing feed retried after a back-off, 1 minute doubling to an hour, behind the others), which close them (4403) and refuse that dependency for 24 hours. A principal's authority is versioned by its lifecycle generation, so sockets opened after an unsuspension are not closed by the suspension's row. Told revocations are kept 7 days |
| Workload | Per socket-day, before turning it on: 144 renewals (each a directory read), up to 200 control messages (each a local row write), a local write a frame, about 10 directory rows written at admission and release. Per pump run that sends: a page of up to 20 changed streams; for each of up to 4 credentials, its check on the directory and the decision of one owning account's repositories in that page (one call to that account's object: at most 4 account calls a run). The measured envelope decides `FYRDEN_LIVE_SOCKETS` |
| Budgets (built, not wired) | The directory keeps live's ledger (migration 0033): a grant pays for a unit of live work before it runs, debited once against the UTC days (D1's clock) it may run on, within live's daily allowance (Proposed, of Free's limits: 30,000 object requests, 2,000,000 rows read and 50,000 written, 20,000,000 ms of object duration, 1,000,000 D1 rows read and 30,000 written; a tenth of each kept for cleanup, and ordinary grants refused while their cleanup debt would pass a twentieth); a retry of the same operation gets the same grant back and never a second charge; duration is held per day (64 unsettled a day) and its unused part refunded once, to its own day; nothing else is refunded. A restore of a feed's object, or of the directory (a new ledger incarnation), invalidates the credit the object held at once; recovery cleans what grants left a bounded page (64 rows) a call, paid for per attempt, and retires a feed's cleanup debt only once the object acknowledges it clean; expired receipts (32 a call) and week-old days (8 a call) are removed with their debt. Nothing grants yet. Still to come before live hints are turned on anywhere: the pump (its run already bounded: a page of 20 changed streams, 4 credentials, each checked again on the directory's primary and deciding one owning account's repositories, a socket's progress stopping at what is left), renewals, controls and maintenance funded through the ledger at measured prices, one outstanding authorization an object, and one invocation budget shared with notification email's sends. A connected call between objects is not cut by the platform at 15 minutes (measured on Free), so a hold is only the duration reserved first: each funded operation on an object is an owner (migration 0035), admitted (all of an operation's owners or none) within the deployment's places and each object's, cleanup's kept from ordinary work, before it is dispatched, holding its place across days and restarts until what it really ran is observed and settled day by day (past its hold charged to the days it ran on, even past a day's allowance, which is then marked, and owed as duration debt served from later days' ordinary capacity; an unused hold refunded only while still in escrow) and released; one whose end cannot be shown is uncertain and keeps its place. Ordinary duration also leaves a daily reserve, the debt owed and what was withheld for it. A feed's alarm admits its work whole against its ceilings (40 D1 statements, 800 internal calls, 40 external fetches; Proposed): its mandatory steps first, then each notification email only if all of it fits (one email measured 8 statements and 6 internal calls, its ceiling 16 and 12); one that does not fit waits as it was (no attempt, no try) for the next run, which is due at once. A feed's recovery fences first (results captured before it never apply; nothing granted through the sequence it recovers is spent again), then deletes what that sequence paid for a page at a time, quarantining (in the directory) the owner of any work it dispatched before forgetting it: clean means its local state is retired, not that the work ended or its places were freed. One authorization runs at a time an object: its result is waited for 10 seconds (then given up on, never applied later), while its work, which the platform does not cut, keeps the object from starting another until it ends; each of its awaits (an account's confirmation among them) is followed by a check that stops it once it can no longer apply. The places, the reserve and its size are not set yet (no production values) |
| Credentials | A session, or a token of the principal itself, not bound to a DPoP key (and not of an agent whose owner requires DPoP): a socket's upgrade carries no key proof |
| Rollout | `fyrden deploy --live on [--live-sockets N]`, passed on every deploy (left out: off again) |
| Web pages | A tab keeps one socket across its pages while one of them listens (the inbox, its digests, an issue's page) and it is shown: opened when such a page is shown, kept through navigations (a minute after the last listening page), let go after 5 minutes hidden. Each socket opened is one of the principal's 60 admissions a day: reloads and new tabs take one each, and so does every reconnect (a renewal that failed, a slow consumer, a dropped network, a deploy, and a socket's 200 controls spent: acknowledgements go every 4 frames or a minute), page-to-page navigation none. A credential holds 5 sockets at once, so a sixth listening tab is refused after its admission: a socket refused before it opens is tried again once, 30 seconds later, then paused. A page reads itself again when a stream it shows changed (hint-driven reads at least 10 seconds apart, none during a navigation or while hidden) and once on every connect. Its ticket comes from `POST /notifications/live-ticket` on the web's own origin. Told live hints are off, the tab asks again an hour later, on the next page or showing; failing (five times in a row, or a socket refused twice), after 10 minutes; revoked or signed out, not until a page is loaded again. Pull request pages do not listen yet |

## Search (not yet served)

Search's projections of issues, pull requests, labels and milestones are kept in the org read model; nothing reads them yet. Writing and repairing them waits for the deployment setting `search_indexing` (`deployment_settings` in the directory database), off until an instance administrator turns it on with `PUT /admin/search/indexing` (`{"enabled": true}`; `false` turns it off again, keeping what was projected). Projections miss what happens while it is off, so turning it on is followed by a backfill (`POST /admin/search/backfill`).

| What | Value |
|---|---|
| Projections | One row an issue or pull request (its state, text, author, labels, assignees and milestone), a label and a milestone, each written only forward (by the source's epoch, ownership and the entity's version) and only while the repository is not deleted; a deletion keeps a row without its text until a reconciliation covers it. Rows written (measured): an issue first projected 6, a change 5, a deletion 2, a label or milestone 2 |
| Live projection | While search indexing is on, the events consumer projects each envelope's newest snapshot of every issue, pull request, label and milestone in the message's own batch (no added D1 call a message; one an invocation settles what its messages reserved). Each batch reserves 16 rows an entity and 14 for its bookkeeping (its admission's 2 included: see Read model writes) from the day's allowance and gives back what it did not use: an issue first projected costs the day 25 rows with the bookkeeping and the admissions of its batch and of the settlement's, its full-text entry, its repository's number, the counters and its growth's receipt (made and released) included, a duplicate delivery 12 (measured 2026-10-31). Past the allowance, or with the database at its size threshold, additions are refused, while a deletion still empties a row already there (one of an entity never projected would add a row, and is refused too). A reconciliation is asked for in the same batch when an addition is refused, a stored snapshot's payload is gone, the repository's epoch advances (a restore), or a snapshot's row cannot be read (that entity is skipped and the rest applied). A batch projects at most 1 MiB of the text search indexes (titles and bodies, names and descriptions) and 200 snapshots (one alone always): an envelope's rest is sent on as a continuation, for search alone (no effect planned or journaled), before the envelope's message is acknowledged (a failed send retries the message, whose writes stand), and a reconciliation is asked for in the first batch (`search_continuation`), so a continuation lost leaves nothing unnoticed. The consumer never looks at the held size again itself: a size at the threshold refuses additions until the repair job's next reservation looks again |
| Full-text indexes | Issues' and pull requests' titles and bodies (with tokens of their repository and kind) and repositories' names and descriptions (with a token of their owner) are indexed with their projections (org migration 0019; FTS5, `unicode61` with diacritics removed, no stemming), each write's index change in the same batch as its row: the old entry deleted while the row still has it, the new one inserted once the row is written, nothing when only other fields change, a duplicate, stale or covered write changing neither. A repository's entry is kept only while search indexes, within the repository index's own allowance (2,000 rows a UTC day, reserved 24 an entry and settled at what it wrote: 21 for one first indexed, measured) and room (20,000 repositories; provisional, until measured): one that changes when it does not fit is taken out, its row still written, and a reconciliation asked for (`repository_index_refused`); one that changes while search does not index is taken out too (the backfill after turning indexing on brings it back), the rows that takes charged as well; a change of one it holds fits a full index (it grows by none). Its row is the read model's. Repositories and owners get numbers of their own for the tokens, never reused; a deleted repository's cleanup takes its documents' entries out before their rows, and its number once none is left. An issue first projected writes 12 rows with its entry (a 9,000-word body as many as a short one; the index's merges now and then more, settled at what is written: a step charges all it wrote, past its reservation too), its group reading about 26 (measured 2026-10-31). A reconciliation puts back the entries of rows the index lacks (projected before it existed, or lost from it), the rows as they are, and the repository's own entry; a delete of an entry the index does not hold is never issued (it would leave the index unreadable). A source is known whole (`search_sources.index_covered`, org migration 0021) once a pass walked all of it with nothing refused and no repair asked for since; a pass starting, or a repair asked for, clears it. FTS5 merges an index's segments a little with every write; the repair job finishes what that leaves, a merge of each index a run (64 pages of work, after its sources' turns, with the calls they left; not when the run found the allowance spent): admitted in a batch of its own (8 rows of the day's allowance and 256 KiB of growth reserved; refused at the size threshold, its batch spent and the other index waiting), settled at what D1 counts its batch and settlement, its receipt's release included (the merge command alone, with its batch's admission: 3 rows written and 6 read, the index's own pages not counted as rows; one merge finished the work left by 300 small commits, 24 of the longest bodies and 300 edits of five issues, one after another, and the database grew by a page at most: measured 2026-10-31). Nothing searches the indexes yet |
| Reconciliation | Compares a repository's projections with its own state and writes only differences: the repository's export, read from one position (200 entities and 2 MiB a page), sets the source's cutoff first (later events at or before it are refused), then 5 pages a call, each comparing at most 200 projection rows and writing at most 1 MiB of the text search indexes (a page past it ends before the entity that would pass it, one alone always); a row a page lacks is marked deleted where that page found it gone (nothing at or before that place changes it again), unless an event after the page was read wrote it; the repository's own row comes last, from a snapshot read then (a page of its own); an entity made and deleted since the export began keeps its deleted row; a restore or transfer meanwhile starts the pass again, and a pass the source's fences refuse waits. Callers working the same page at once: the first one's writes stand. Deletions a cutoff covers are removed once a pass ends, 500 a table (Proposed); a deletion of unknown position (an issue deleted before positions were recorded) stays. A source is visible to search while its row's recovery generation is the read model's (`search_sources.visible_gen`, `search_index_state.recovery_gen`; org migration 0024), or it has no row (nothing of it was restored): raising the generation, as a recovery does, hides every source with a row at once, a pass started before it writes nothing more and a new one follows, and only a whole pass started under the current generation makes its source visible again (a rebuild of the indexes never does) |
| Repairs | A source needing a reconciliation is recorded once until a pass covers it (a need during a pass asks for another after it). The five-minute maintenance works them in a request of its own (an invocation's own calls: at most 40 a run, an application limit, its writer's lease's two directory calls, the size its work left and the repositories' export pages among them; a step starts only when all it may call fits, 11 at most), oldest first, 1 export page a source a turn and 20 in all a run (Proposed), a source not finished in its turn, or failing, going behind every one still waiting. A source whose pass ended partial (its growth, its repository's index entry, or an issue's entry refused, or the database at its size threshold; `search_repairs.blocked_reason`, org migration 0022) is parked for 5 minutes, out of the queue, and a run wakes at most 2 whose wait is over, at their place. A run whose turn found search's allowance spent puts that source behind the others, sweeps covered deletions once and stops; nothing while search indexing is off |
| Backfill | An instance administrator asks for every active repository's reconciliation with `POST /api/admin/search/backfill` (100 repositories a call; call again with the returned `next_cursor` until it is null); a repository already waiting is not asked again, and the requests are charged to search's allowance as if each wrote its row (5 rows, the source's coverage cleared with it). It is refused while search indexing is off: it runs once indexing is on, so a repository made meanwhile, behind the backfill's place, is projected from its events instead; one published more than 5 minutes after its storage was made (a fork's long copy), whose first events the consumer may have dropped as a repository never listed, asks for its own reconciliation (a failure to ask is logged, `search.published`, and made good by running the backfill again). The repair job then works them as any other need, so populating a deployment's projections takes as many days as their rows need of the allowance |
| Allowance | Search may write 40,000 projection rows a UTC day and its reconciliations read 1,000,000 rows (as D1 counts them), and at 350 MB of org database (Free's limit is 500 MB; the rest is left for effects and webhooks) adds nothing more: a reconciliation then only removes (marks deleted what is gone, which empties its text), and covers no repair (a whole pass follows once there is room); all Proposed. Each step reserves its worst case before it runs and gives back what it did not use (its bookkeeping charged too); a step whose day ends before it reads or writes reads and writes nothing and runs again from the next day's allowance. The size held is the latest any read model writer observed (its work's last commit, recorded once as the work ends, effects' and webhooks' included, ordered by the executor's commit sequence). Every batch that adds to the projections also reserves the growth it may make (its rows' JSON bytes, times 4, and 64 KiB an entity; measured 2026-10-31 in workerd, through the consumer's path, as the larger of D1's size after and the bytes the index and text added: a batch grew the database by at most two thirds of what it reserved, a body of distinct terms about three times its JSON, a small edit after an index of large documents up to seven pages (the index's merges, by what came before), over short, repetitive, distinct-term, three- and four-byte and combining text, the longest titles, a hundred labels, inserts, replacements, deletions, batches of ten and small edits; an entity wrote at most 12 rows and read 40, of the 16 and 48 it reserves; remote D1 not measured) in its own transaction, with a receipt of its executor sequence, admitted only while the size held, every growth still reserved and its own stay within the threshold; an observation releases the receipts it covers, the oldest 100 at once (a lost settlement's too, by the next observation any writer records). One at the threshold is looked at again before a refusal, so a database that shrank is let through. Removing deletions a cutoff covers is counted but never refused. With the day's allowance spent, reconciliations wait, and the repair job instead sweeps covered deletions of any repository (500 of each table looked at a run, after where the last sweep stopped) |
| Read model writes | Every write to the org read model goes through one executor: a writer leases itself in the directory at its first write (3 directory rows written taken and released, 2 a renewal, measured; a lease lasts 15 minutes, renewed once half has passed), and each batch it writes opens admission first and closes it last in the same transaction (2 rows more a batch, measured), refused whole unless the read model's barrier is running at the lease's generation, the lease's protocol is at least the read model's (2) and the lease's deadline is ahead by the database's clock. Work that writes rarely (a digest's credit, a late repository's reconciliation request, a backfill page) takes a lease of each write's own. A write to the read model's tables made outside admission is refused, its whole batch with it (`read_model_admission_required`; org migration 0018: before it, such writes were only counted, in `read_model_write.stray`; `fyrden deploy` installs it over a read model that holds data only with `--quiesced on`, for a test deployment with nothing running: an upgrade with work running is not supported); the barrier is changed only by the pause and resume steps, as maintenance writers (a lease of each write's own, taken while the directory's barrier is not running and still at the generation the step decided on), and never to an older generation. Every write to those tables reads the admission row and the barrier (2 rows more read for each row written, from 0018). Leases whose release was lost are removed by the five-minute maintenance once their deadline passes, 500 a run (Proposed) |
| Read model maintenance | With `FYRDEN_READ_MODEL_MAINTENANCE=on`, API writes (REST and MCP; every method but GET) answer 503 `read_model_maintenance` with `Retry-After: 300`, and pushes are refused (git prints why; a push already past its discovery gets 503); the events, dead-letter, webhook and effect queues put each message back on its queue for 5 minutes, as JSON as it was sent (a new message: no attempt spent; one that cannot be put back is retried); the effects cron, search repairs, deletions' cleanups, abandoned generations' settling, transfers' fences and pruning failed envelopes wait; a repository's digest credit asks again in 5 minutes (all Proposed). Each message held costs its three queue operations again every 5 minutes, 864 a day: on Free's 10,000 a day, a dozen messages held all day spend them, so keep maintenance short. A pause moves the shard's barrier in the directory to the next generation (no lease taken or renewed from then on) and then the read model's own (no batch of an older generation admitted), and is paused once no older lease is live; resuming sets the read model's barrier running first. A read model whose barrier is ahead of the directory's (the directory restored) is caught up: a pause moves past it, a resume moves the directory's up to it first |
| Read model export | Available once `fyrden deploy` has recorded the restore floor (the org database's bookmark taken once writes outside the executor are seen refused; before it, `no_restore_floor`): `fyrden read-model export` (backup.md) pauses the writers (`POST /api/admin/read-model/pause`, a step a call; allowed, with `…/resume`, while maintenance holds other writes back), then reads the manifest (`GET /api/admin/read-model/export`) and every page (`GET /api/admin/read-model/export/pages`, instance administrators): every table of the read model in key order, 200 rows or 2 MiB of JSON a page at most, its framing included (Proposed; a row whose JSON is larger, as a retained envelope's escaped text may be, is a page of its own, within D1's limit on a row), rows read about a page's worth at a time, all under the barrier paused at one generation (checked in each read; a moved barrier refuses the next page: 409 `export_fence_lost`), with a manifest of the migrations, the generation, each table's columns and the protocol's state; the command writes each table's rows and their SHA-256, then resumes the writers. Importing an export is not built yet: restore with D1 Time Travel, to a bookmark at or after the floor |
| Index checks and rebuilds | `POST /admin/search/indexes/check` (instance administrators) checks a full-text index (`documents`, `repositories` or `both`, in that order) against the projections it is built from, each on its own (FTS5's integrity check against its content): not matching while some live projections are not in it yet (projected before it, or their growth refused), until a backfill reconciles them. Allowed at the size threshold; each check charged to search's spending as a write of its own (D1 counts none of the index's own reads). `POST /admin/search/indexes/rebuild` makes a small index again at once from its projections and marks them indexed (their count set): at most 256 live projections and 1 MiB of their text an index (`index_rebuild_too_large` past either), none left out of its content (`index_reconcile_required` while a live issue's repository has no number), both looked at first (bounded reads: one past the limit, the repositories through an index of those the index holds, org migration 0023) and each still within the limits when it is rebuilt (they may grow between); admitted within search's allowance and growth as any other write, reserving for the most a rebuild may hold (520 rows, 20 MiB; `index_rebuild_refused`), and settled at what D1 counts with its look and both writes' leases. It repairs an index, not the projections: no repository becomes known whole by it |
| Recovery preservation | Before a restore, a recovery (one a shard at a time, recorded in the directory: directory migration 0038) keeps every row and column of the read model's operational tables (`consumer_epochs`, `discretionary_hours`, `discretionary_state`, `effects`, `events_failed`, `search_budget`, `source_owner`, `webhook_attempts`, `webhook_deliveries`, `webhook_payloads`), started only while both barriers are paused at one generation, with a fresh id (1 to 64 letters, digits, `_` or `-`, never used before), at the next generation, the directory's barrier `recovering` at it (nothing resumes the writers under it) and the read model's paused at it (a resume already under way admits nothing more): a step a page of one table (200 rows and 256 KiB of the rows as stored, a larger row alone; its keys and sizes read first, then only the rows that fit; 5,000 pages a recovery at most, past which it is refused: recover into a fresh database instead), read under the paused barrier's fence, each value typed (an integer as its decimal text, so none rounds), digested (SHA-256) and written to `fyrden-assets` under `read-model-recovery/<recovery>/` (its digest in its name; nothing prunes the prefix), catalogued in the directory with its rows, bytes and last key (its place moving on only past the page as recorded), then sealed under the same fence into a manifest of every page's digest and its own. A page read back is checked against its record, the manifest and its digest; a step repeated finds its page recorded. Search's projections are not kept: they are reconciled again |
| Read model status | `GET /admin/search/status` (instance administrators): the write protocol (the executor version served, the one the last `fyrden deploy` verified as served and recorded, the oldest admitted; `enforced` once writes outside the executor are refused, `compatibility` before; the restore floor), the restore token (`uninitialized` until the first handshake, `matched`, `intent`, or `mismatch`: the read model restored or changed since the last handshake; `POST /admin/read-model/handshake`, `fyrden read-model handshake`, refuses to replace an unknown one), both barriers and whether they agree, the admission row (the `stray` count from before, and the write sequence), live and expired leases with the earliest deadline, whether a coherent export can be made (not until a restore floor is recorded: `no_restore_floor`), and search's day, its spending of its allowance and of the repository index's with their limits, the size observed and the growth reserved since, the documents and repositories its full-text indexes count, the next due reconciliation, the parked one whose wait ends first (with why) and a repository not known whole (each source is certified alone: none listed does not mean a backfill reached every repository). A few singleton rows, one row each through the due, retry and uncovered indexes, and the shard's leases (few: expired ones are reaped every five minutes). `/healthz` names the protocol served (`readModel.protocol`), even when its checks are rate limited; a deploy that cannot read it records nothing and says so |
| Failed events | An envelope of events the consumer gives up on (after 10 tries) is stored from the events dead-letter queue before its dead letter is acknowledged: a repository's asks for its search projections to be reconciled (none for a deleted repository, whose record alone is kept); an account's waits for an operator to replay it (the replay operation is not built yet); one that cannot be read is kept with why. A malformed one keeps the source it names (fenced and purged as any other) and says what was wrong by kind only (never text from the envelope; its events are validated one at a time, stopping at the first invalid one, and more than 1,000, past what any envelope carries, not at all); one JSON cannot hold is recorded without its body, as is one over 1.9 MB as JSON, nested more than 64 levels deep, or taking more than 1.9 million reads to measure (a part shared many times over); one reading fails on in any other way is kept as unreadable, with no source. Envelopes are kept 14 days, the record of each failure after that (Proposed); a deleted repository's go with its cleanups. A dead letter that cannot be stored either (the org database refusing it through 10 more tries) is lost with no record: a repository's lost events are then found only by its next reconciliation; watch the `events.failed` metric and the queue's backlog, and reconcile the affected repositories |

## Idempotent requests

A REST write (any method but GET) sent with an `Idempotency-Key` header runs
once per token and key; it is optional, as on GitHub. MCP tool calls take no
key. The key is checked after the token (revocation included), the rate
limit, the token's scopes and the input; a replay returns the answer the
same token already got, without checking its access to the repository
again.

| What | Value |
|---|---|
| Key | 1-255 printable ASCII characters (else 422 `invalid_idempotency_key`), per token |
| Kept | 24 hours, then forgotten (the cron deletes expired keys) |
| A retry of the same request | The first answer again, with `Idempotent-Replayed: true`; nothing runs twice |
| The same key, another request | 422 `idempotency_key_reused` (another operation, or another input) |
| While the first still runs | 409 `idempotency_key_in_use` with `Retry-After: 5` |
| When the first may or may not have taken effect | 409 `idempotent_outcome_unknown`: it failed unexpectedly, or was still marked running after 10 minutes. Check, then use a new key |
| Answers not kept | 401, 403, 408, 429, `busy`, `network_busy` (whatever the request began was undone: a retry runs again), and an upload's completion while it is still indexing |
| Answers with a secret (minting a token) | Not kept: a retry answers 409 `secret_already_disclosed` naming the token made |
| Largest answer kept | 256 KiB; a larger one answers a retry 409 `idempotent_replay_unavailable` |

## Not supported

- Git LFS.
- SHA-256 repositories (`object-format=sha256`); repositories use SHA-1.
- Protocol v0 and v1 for fetch and clone, and the dumb HTTP protocol.
- Server-side hooks (`pre-receive`, `update`, `post-receive`).
- Partial clone (`--filter`) and the other fetch features listed above.
- SSH; git is served over HTTPS.
